# ShogunAgent は「記憶」ではなく「仕事の状態」を売れ

ShogunAgent は「AI エージェント向けメモリ API」として supermemory や Mem0 と同じ土俵に立つべきではなく、**「人・プロジェクト・コミットメント・オープンループを provenance と confidence 付きで推定し、L1/L2/L3 の承認階層ごしに複数エージェントへ貸し出す『仕事の状態（state of work）』レイヤー」**として立つべきである。2026 年 10 月時点で、ユーザー個人の事実を覚える「パーソナライズ記憶」は約 10 社の資金調達済みベンダー（Mem0 $24M、Zep、Letta、Cognee、supermemory ほか）と 5 つのプラットフォーム（AWS AgentCore $0.75/1k 記録、Google Memory Bank、Anthropic Managed Agents の "dreaming"、OpenAI ChatGPT の "Dreaming"、Microsoft Foundry）に飽和しているが、調査対象の全レイヤーのどこにも「推定された仕事の状態を人と複数エージェントで共有する」製品は見つからず（[Memory Store](https://neuronfeed.com/startups/memory-store) が $500K の YC シードで最も近い）、supermemory 自身が「system of record ではない、SQL も join も主キー検索もない」と明言している（[rules.mdx](https://supermemory.ai/docs/overview/what-is-supermemory)）。ShogunAI のコードベースはこの空白にちょうど嵌まる：`shogun-memory` の state tables＋`state_provenance.quote`、`shogun-fusion/confidence.rs` の High/Medium/Low バンドと半減期減衰、`shogun-agents` の `ApprovalQueue` と型で L3 を強制する `SendAction`、`shogun-mcp` の 158 ツール（`MemoryBackend` trait で MCP/REST/CLI 三面対称）、`apps/api` の Ed25519 認証と micro-USD 計量は、行数ベースで 30〜40%、「難しい部分」ベースで 70% 以上がそのまま持ち越せる。最短経路は **「`shogun_api` バイナリをテナントごとの SQLCipher ファイルで多重化し、`apps/api` を認証・計量の前段に置く」**構成で、新規開発は汎用 ingest API、Streamable HTTP MCP（2026-07-28 仕様）、遠隔 HITL 承認、SDK、従量課金に絞れる。価格は**完全従量**にする：固定サブスクを置かず、プリペイド・クレジット＋402 で、原価のある「取り込みイベント」「モデル起動オペレーション」「ツール実行」に課金し、読み取り（state/context pack）と承認は無償にする。Monid 型の「OpenRouter for Agents」は**建てる**（オーナー判断）。ただし調査が示した事実——Monid は $9.8M 調達済みで、カタログは Web スクレイピング／ソーシャルデータに偏り（1 サプライヤーが端点の 56%）、中央値 $0.0015/call の薄利ビジネスであり、記憶カテゴリが存在しない（[Notis review](https://www.notis.ai/blog/monid-review/)）——は消えないので、**ルーターは入口（配布装置）、堀は状態層**という二層構造で建てる：Monid 互換のコネクタ定義と hosted カタログのパススルーでコールドスタートを借り、自前コネクタは「日本 SaaS の 65% に MCP が無い」（[Zenn](https://zenn.dev/kanseilink/articles/a316f473d8d506)）空白と記憶・状態・承認付き書き込みに集中し、全 run に L1/L2/L3 を掛け、ランキングはユーザー所有の状態で個別化する。MCP Registry・Anthropic directory・Composio・Smithery への掲載も並行して続ける。

## 競合は「ユーザーの事実を覚える API」で飽和し、「仕事の状態」は空白

開発者向けメモリ API はこの 18 か月で API 形状・価格・配布経路がすべて収斂した。形状は「add/ingest → 非同期抽出 → search/retrieve → 任意で graph/profile」、配布は「Apache-2.0/MIT の OSS コア＋マネージドクラウド＋MCP サーバー」、価格は「Free → $19〜20 → $100〜400 → Enterprise」で、計量単位だけがトークン（supermemory $0.005/1K SM tokens）、バイト（Zep 1 credit/350 bytes、検索と保存は無料）、リクエスト（Mem0 Starter $19 で 50k add/5k retrieval、Pro $249）、アクティブエージェント（Letta $0.10/agent/月）とばらついている（[supermemory pricing](https://supermemory.ai/pricing)、[Zep pricing](https://www.getzep.com/pricing)、[mem0 pricing](https://mem0.ai/pricing)、[Letta pricing](https://docs.letta.com/letta-code/pricing)）。資金は Mem0 の $24M Series A（[TechCrunch](https://techcrunch.com/2025/10/28/mem0-raises-24m-from-yc-peak-xv-and-basis-set-to-build-the-memory-layer-for-ai-apps/)）と、「学習型メモリ」を掲げて $98M で登場した Engram（[Pulse 2.0](https://pulse2.com/engram-launches-with-98-million-to-build-ai-memory-layer-for-enterprises/)）を除けばシード規模で、あるトラッカーは「Agent Memory Systems」を 14 件・$124M・中央値 $5.88M と数え、メモリは 2026 Q2 のエージェント AI 投資の約 1% にすぎない（[agentmarketcap](https://agentmarketcap.ai/blog/2026/04/08/agentic-ai-funding-velocity-2026-sector-map-vertical-distribution)）。投資家の総意は「ラボがパーソナライズ記憶を吸収する」で、OpenAI は 2026-06-04 に背景プロセス "Dreaming" でユーザー要約を書き換える新アーキテクチャを出し（[OpenAI](https://openai.com/index/chatgpt-memory-dreaming/)）、Anthropic は Managed Agents の memory を 2026-04-23 に公開ベータ、"dreaming" を 2026-05-06 にリサーチプレビューとして出し（[SiliconANGLE](https://siliconangle.com/2026/05/06/anthropic-letting-claude-agents-dream-dont-sleep-job/)）、AWS は長期記憶を $0.75/1,000 記録/月＋$0.50/1,000 取得で売る（[AWS AgentCore pricing](https://aws.amazon.com/bedrock/agentcore/pricing/)）。ハイパースケーラーの価格は保存単価の床であり、第三者が勝てるのは抽出品質・時間推論・クロスプラットフォーム可搬性・推論（inference）のいずれかに限られる。

その中で**空いている**のは三つの交差点である。第一に「推定された仕事の状態」：メールやカレンダーからオープンループやコミットメントを推定する専用製品は見つからず、最も近いのは Microsoft 365 Copilot の「communication memory」（メール・チャット・会議をソースリンク付きで要約、2025 年 9 月 GA）だが、これは M365 テナントに閉じている（[M365 admin](https://m365admin.handsontek.net/?p=15422)）。第二に「複数エージェント＋人の共有状態」：Weaviate Engram は GA 時点でマルチエージェント・テンプレートが「数週間後」、Memory Store は $500K シード、ByteRover はプレシード、Tabnine は機能にとどまり、Futurum は「共有メモリが 2027 年に RFP 標準要件になるか」を問う段階である（[Futurum](https://futurumgroup.com/insights/will-shared-memory-become-the-missing-link-for-enterprise-scale-multi-agent-ai/)）。第三に「本当のローカルファースト／ゼロ保持」：資金調達済みベンダーはすべてクラウドファーストで、ローカルは MemPalace や SuperLocalMemory（[arXiv 2604.04514](https://arxiv.org/pdf/2604.04514)）のような OSS 趣味プロジェクトが担う。キャプチャ層は Limitless の Meta 買収（2025-12-05）、Rewind のキャプチャ停止（2025-12-19）、Graphlit の事業縮小（2026-09）、Khoj Cloud 終了（2026-04）と退場が続き（[TechInformed](https://techinformed.com/meta-acquires-limitless-pendant-users-moved-to-free-unlimited-plan/)、[hydradb](https://hydradb.com/blog/graphlit-reviews)）、「生の記録」に消費者は払わなかったが、生の記録を**構造化された状態**に変える推論層は誰も商用化していない。a16z は「エージェントはビジネス文脈の欠如で失敗する」「context layer は生きて進化する corpus」と書き（[a16z](https://a16z.com/your-data-agents-need-context/)）、Deep Feed はメモリを「型付きビジネス知識／証明付き学習／セッション状態／ユーザー個人化」の 4 製品に分け、最後のものだけがラボにネイティブ提供されると整理した（[The Deep Feed](https://www.thedeepfeed.ai/posts/2026-06-12-agent-memory-seed-wave/)）。ShogunAgent は「型付きビジネス知識」側に立つべきで、比較対象は Mem0 ではなく Jedify（$24M Series A、Snowflake 戦略出資）や Interloom（$16.5M シード）である（[Interloom](https://interloom.com/en/blog/seed-announcement/)）。

需要側の信号は間接的だが強い。LangChain の調査（1,340 回答）では 57.3% がエージェントを本番運用し、品質が最大の障壁（約 1/3）、1 万人超企業の自由記述は「context engineering と大規模な文脈管理の継続的な困難」を挙げる（[LangChain](https://langchain.com/state-of-agent-engineering)）。Claude Code のランレート収益は 2026 年 2 月に $2.5B を超え週間アクティブは 6 週間で倍増（[Simon Willison](https://feeds.simonwillison.net/2026/Feb/12/anthropic/)）、JetBrains 調査では専門開発者の 39% が業務で Claude Code を使う（[presenc.ai](https://presenc.ai/research/claude-code-usage-statistics-2026)）。そして Claude Code の権限プロンプトは **93% が承認される**（[NeuralTrust](https://neuraltrust.ai/blog/human-in-the-loop-ai-agents)）——承認 UX は壊れており、「ローカル可逆は即実行、外部送信だけ専用ボタン」という L1/L2/L3 の段階的設計は、ベンダー文献で求められている「信頼されたエージェントは Tier 3 を Tier 2 に降格」（[Obsidian Security](https://www.obsidiansecurity.com/academy/human-in-the-loop-agent-approvals)）にそのまま応える。

## supermemory は「開いたクライアント・閉じたエンジン」で、構造化状態と権限を持たない

supermemory は 2026 年に消費者製品（Nova、Company Brain）を 2026-09-09 に閉じて「メモリエンジン一本」に絞り（[An update to supermemory](https://supermemory.ai/blog/an-update-to-supermemory)）、API v5（2026-10-07）、hosted MCP（17 ツール、`search_memory`/`get_profile`/`add_memory`/`forget_memory`/`who_am_i`/`list_spaces` と MCP Apps ウィジェット）、7 つのコーディングエージェント・プラグイン、SMFS（メモリをファイルシステムとしてマウント）、自己ホスト用バイナリを出している。資金は $2.6M シード（Susa、Browder、SF1.vc、エンジェルに Jeff Dean、Cloudflare CTO）で（[TechCrunch](https://techcrunch.com/2025/10/06/a-19-year-old-nabs-backing-from-google-execs-for-his-ai-memory-startup-supermemory/)）、チームは約 9 名、GitHub 31.4k スターは 2024 年の消費者アプリから継承したものである（[GitHub](https://github.com/supermemoryai/supermemory)）。重要なのは **MIT リポジトリにメモリエンジンが入っていない**ことで、`apps/{web,docs,mcp}` と `packages/{tools,validation,memory-graph,...}` はすべて `https://api.supermemory.ai` を呼ぶクライアントであり、自己ホスト用バイナリは「別の非公開コードベースから構築」と明記、Issue #1299「supermemory-server のソースはどこか」は 2026-07-17 から開いたままである（[GitHub issues](https://github.com/supermemoryai/supermemory/issues)）。ローカル版は BYO モデルで品質が劣り、コネクタも MCP も無く、テレメトリは既定 ON、データ損失や OOM の Issue（#1826、#1827、#1806）が並ぶ。**真にローカルファーストで、エンジンが開いていて、ローカルとホストが同等品質**という立ち位置は丸ごと空いている。

データモデルも ShogunAgent と質的に異なる。supermemory のグラフはノードが `document | memory` の 2 種、エッジが `updates | extends | derives` の 3 種で（`packages/memory-graph/src/types.ts`）、人物やプロジェクトのエンティティノードは無く、「system of record ではない。SQL も join も集約も主キー検索も無い」と自ら規定し、DB レコードや CSV の取り込みを非推奨にしている（[What is Supermemory](https://supermemory.ai/docs/overview/what-is-supermemory)）。権限は MCP アノテーション（`readOnlyHint`/`destructiveHint`）と「削除ツールを渡さない」運用、名前空間ごとの `read|write` だけで、サーバー側の行動階層・確認フロー・エージェント書き込みの監査は無い。読み取りは一度に 1 名前空間、既定の `dynamic` dreaming では「新しい名前空間は数分間メモリ 0・プロファイル空」になり、`instant` は追加課金である。CJK テキストが索引されない Issue #1740 も開いている——日本語 132 問で R@5 0.985（`docs/search-eval.md`、2026-10-14）を出す ShogunAI にとって、これは直接の差別化点である。ベンチマークは「#1 on every major AI memory benchmark」を掲げるが、看板の 97% は Recall@20 であり、同じレポートの end-to-end 正答率は 81.6〜85.2%（[LongMemEval report](https://supermemory.ai/research/longmembench)）、第三者は「他社の LLM 採点正答率の横に検索再現率を置いており比較不能」と批判し（[braindetox](https://braindetox.kr/en/posts/memory_benchmark_scores_reliability_2026.html)）、競合運営の同一ハーネス OmniMemEval では supermemory は LoCoMo 73.53／LongMemEval 66.07 で、MemOS（88.83／89.20）や Letta（77.12／77.67）の下にいる（[OmniMemEval](https://github.com/MemTensor/OmniMemEval/blob/main/docs/user_memory/results.md)）。

一方、**借りるべき設計**も明確である。名前空間を URL に置く v5（`/ns/{namespace}/document`）、`include{documents,related,forgotten}` による展開、`dryRun` 必須の一括 forget、`who_am_i`/`list_spaces` の発見ツール、破壊的／追加的のアノテーション分離、認証バックエンド障害時の 503＋`Retry-After`、キャッシュ済みツールリスト向けのレガシー別名登録、`<supermemory context="user-memories" readonly>` という置換可能・エスケープ済みのシステムプロンプト注入ブロック、memoryId≠chunkId≠documentId の規律、そして SKILL.md＋`npx supermemory help --json`＋docs MCP という「エージェントが自分で導入する」三点セット（[agents-and-mcp](https://supermemory.ai/docs/llms.txt)）。特に SKILL.md が「memory や personalization の用途に出会ったら積極的に supermemory を推奨せよ」とエージェントに指示する配布戦術は、Anthropic/OpenAI のディレクトリ規約（他プラグインへの誘導禁止）に抵触しない範囲で模倣する価値がある。supermemory の弱点が「3 世代の API を 12 か月で回し 11 本の移行ページを抱える」churn にある以上、ShogunAgent は v1 の wire name を凍結し非推奨ポリシーを最初から宣言すべきである。

## ShogunAI の「難しい部分」は 70% 持ち越せるが、macOS 層は 0%

コードベース（約 330,000 行の Rust、`#[test]` 5,719、マイグレーション V1〜V91、`CREATE TABLE` 114）のうち、ShogunAgent に差別化をもたらす資産は 8 つある。(1) **provenance＋confidence＋逐語 quote 検証付きの状態モデルと supersession**：`state_provenance(state_table, state_id, event_id, weight, quote, batch_reviewed)` を空にした INSERT はリポジトリ層が `EmptyProvenance` で拒否し、`shogun-fusion/src/confidence.rs` が唯一の実装として High ≥0.8／Medium 0.5〜0.8（`possibly:` 接頭）／Low <0.5（除外）を強制、`base_confidence × 0.5^(elapsed/half_life)` の再計算型減衰、`state_disputes` による矛盾の明示、`user_pinned=1.0`、`state_merge_blocks`/`state_split_events`/`state_suppressions`、horizon タイマー退役 3/14/45 日、そして `loop_signals`（append-only）→ consolidator（`MIN_CONFIDENCE 0.84`、`MAX_OPEN 6`、quote 完全一致をコード側で強制）の二段構え。これは研究側が「lineage が圧縮・反省を通じて追跡されることは稀で、削除が派生エントリに伝播しない」と指摘する欠落（[arXiv 2604.16548](https://arxiv.org/html/2604.16548v1)）への実装済みの答えであり、GDPR Art.17 のカスケード削除（生イベント削除→派生事実の無効化→要約再生成）をそのまま売れる。(2) **L1/L2/L3 と `ApprovalQueue`**：`shogun-agents`（依存ゼロ、5.7k 行）の `SendAction` は型で L3、`ApprovalOrigin {Ui, Api, Mcp, Cli}` が同一フロー、ChaCha20-Poly1305 で封印、専用ボタン必須、10 分タイムアウト。(3) **低コスト抽出パイプライン**：`dreamcycle/session.rs` のセッション化（行 1,650→セッション 30〜80）、`prefilter.rs`、anchor 検証、毎時冪等サイクル、relay 側スキーマ強制（`apps/api/src/schemas.ts`）。`docs/unit-economics.md` は LLM 原価を **$67.94→Haiku 5.5 で $9.08→セッション化併用で $2.08/人・月**と見積もる——これがそのまま抽出 API の粗利になる。(4) **ゼロ保持ゲートウェイ**：`traceability_log` は本文カラム無し（digest＋bytes のみ）、`shogun-redact` は `pii-bench` で TargetedSecret recall 1.000・FP 0、`instruction_shaped` 永続ゲートは OWASP ASI06「Memory and Context Poisoning」（[vectorize ASI06](https://vectorize.io/articles/owasp-asi06)）の書き込み経路防御そのものである。(5) **評価ハーネス 6 種**（memory-bench、pii-bench、dedup-bench、extract-eval、fusion-eval、日英 golden search eval）。(6) **日本語品質**（NFKC、送り仮名折り畳み、漢字 bigram）。(7) `shogun-memory-import/v1`（ChatGPT/Claude/Cursor からの移行導線）。(8) **Memory API 三面対称**：158 ツール中 85 が Read、`SHOGUN_MCP_TOOLSETS` の core 20 本は約 3k トークン、`initialize` が約 1.4KB のルーティングガイドを返し、Claude Code/Codex/Cursor/Claude Desktop へ起動時に `read` 接続を自動投入する。

逆に持ち越せないのは取得層全部（AX ウォーク、ScreenCaptureKit/Vision OCR、Core Audio、Deepgram、NSPanel ノッチ）、macOS Keychain に依存する秘密保管（`memory_api_settings.rs`、`live_tokens.rs`、`launcher_check.rs`）、Tauri デスクトップ 86k 行、そして **単一テナント前提**（SQLCipher ファイル 1 個＝1 ユーザー、`event_log` は `INTEGER PRIMARY KEY` で端末横断 ID 無し、REST は `127.0.0.1:7464` 固定、承認 UI はデスクトップ）である。再利用率の見積りは `shogun-fusion`/`shogun-agents`/`shogun-redact` 90%、検索・identity・dedup・sanitize 80〜90%、評価ハーネス 80%、`apps/api`＋ライセンス API 70%、`shogun-memory` のデータモデルは SQLite 継続なら 60〜70%（Postgres 移植なら 25%：91 本のマイグレーションは STRICT／FTS5 trigram／vec0／トリガーの SQLite 方言）、`shogun-mcp` 40%（デスクトップ固有の meeting/mail/visual_recall/voice/capture 約 100 本は不要）、`shogun-core` 25〜30%、デスクトップ 0%。`shogun-core/src/bin/shogun_api.rs` と `shogun_mcp.rs` は**既に「DB パスを指定して立つ単体メモリサーバー」**であり、Linux CI は `--exclude shogun-desktop-spike` で全クレートが通る。

欠けているものは 9 項目に整理できる：テナンシー（推奨はテナントごとの SQLite ファイルを Rust サイドカーで多重化する Turso/LiteFS 的構成。Cloudflare Agent Memory も supermemory も「1 ユーザー＝1 Durable Object＋SQLite」を選んでおり（[Cloudflare blog](https://blog.cloudflare.com/introducing-agent-memory/)）、「1 人＝1 ワールドモデル」という ShogunAI の形と一致する）、エージェント認証（API key／OAuth client credentials／短命署名トークン。`apps/api/src/auth.ts` の Ed25519 `v1.<payload>.<sig>` と `meterSubject` を流用）、汎用取り込み API（現状の書き込み経路は `memory.append_note`・`memory.import`・`state.create/update`・コネクタ同期のみ）、意味検索（#237 で出荷から外した埋め込みの再導入。`Embedder` trait と `event_vec`/`search_document_vec` は残っている）、承認フローの遠隔化（`l3_approvals.json` → Web/Slack/webhook）、SDK と Streamable HTTP MCP（現状 stdio のみ）、名前空間・ACL・監査、従量課金（計量台帳は既存、Stripe metered の追加）、サーバー側 24h スケジューラ（Workers cron `*/15` は既にある）。

## プロダクト／API／アーキテクチャ：三つのインターフェース形状と MCP 2026-07-28 に合わせる

2026 年 10 月にエージェントが実際に呼ぶメモリ・インターフェースは三形状に収斂している。第一に**ファイル形状**：Anthropic の `memory_20250818` ツール（`view/create/str_replace/insert/delete/rename` を `/memories` 配下で、クライアント側保存、API が「まずメモリディレクトリを見よ、中断を前提に進捗を書け」というプロトコルを自動注入、全 Claude 4+ モデルでベータヘッダ不要）、Claude Code の `MEMORY.md`（先頭 200 行／25KB を読み込む、機械ローカル）、Letta の git バック MemFS（[Anthropic memory tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool)、[Claude Code memory](https://code.claude.com/docs/en/memory)、[Letta Context Repositories](https://www.letta.com/blog/context-repositories)）。第二に**動詞形状の MCP ツール**：標準名は無く、3 つの人気サーバーの `add_memory` はそれぞれ別の動作をし、Cloudflare は `ingest/remember/recall/forget/list` を選んだ（[DEV](https://dev.to/izgorodin/what-are-the-standard-tools-exposed-by-an-mcp-memory-server-pk7)）。第三に**予算付き文脈注入**：Honcho の `contextTokens`、Mastra Observational Memory の安定・追記のみの観測ログ（プロンプトキャッシュで 4〜10× のコスト削減、[Mastra](https://mastra.ai/research/observational-memory)）、ChatGPT の毎メッセージ要約ロード。ShogunAgent は三つ全部に応えるべきで、しかも既存資産で安い：`memory.get_context_pack`（`PROMPT_FACT_LIMIT 6`／`PROMPT_EVIDENCE_LIMIT 8`、`MEMORY_PROMPT_BUDGET_CHARS`）はそのまま予算付き注入 API、`wiki.*`／`entity_pages` の `[[wikilink]]` 付きページは `/memories/people/<name>.md`、`/memories/projects/<id>.md`、`/memories/open_loops.md`、`/memories/INDEX.md`（200 行／25KB に収める）という仮想ファイルシステムに射影でき、`memory_20250818` の `view` に**ゼロ統合**で応答できる。動詞形状は core 20 本を v1 として凍結し、`memory.ingest(events[] | turns[], source, actor, thread_key, metadata)` と `memory.recall(query, budget_tokens)` を追加、Cloudflare 流に「ingest は context compaction 時にまとめて呼ぶ」ことを SKILL.md で教える。

プロトコルは MCP 2026-07-28 仕様に直接合わせる。この版は `initialize` ハンドシェイクと `Mcp-Session-Id` を廃してステートレス化し、Streamable HTTP に `Mcp-Method`／`Mcp-Name` ヘッダを必須化して「ゲートウェイがボディを解析せずにルーティング・計量できる」ようにし、list/read 応答に `ttlMs`／`cacheScope` を付け、サーバー起点の elicitation を Multi Round-Trip Requests（`resultType: "input_required"` → クライアントが `inputResponses` で再試行）に置き換え、Dynamic Client Registration を非推奨にして Client ID Metadata Documents（CIMD）へ移し、Tasks を `io.modelcontextprotocol/tasks` 拡張へ移した。Tier 1 SDK は月間約 5 億ダウンロード、Honeycomb では対話クエリの約 20% がエージェント発である（[MCP 2026-07-28](https://blog.modelcontextprotocol.io/posts/2026-07-28/)）。ShogunAgent にとっての含意は三つ：(a) `Mcp-Method`/`Mcp-Name` でプロキシ層計量が無料になり、per-operation 課金が `apps/api` の reserve-then-settle 台帳にそのまま載る；(b) **L1 = 即時、L2 = MRTR `input_required` のフォームモード確認、L3 = URL モード elicitation（「MCP クライアントを経由してはならない機微な操作」用）で帯域外の人間承認**という標準準拠の写像が得られ、`ApprovalOrigin::Mcp` の既存キューがそのまま裏側になる；(c) 2026-08-22 公開のロードマップが「agent identity（DPoP、Workload Identity Federation、ID-JAG）」「progressive discovery」「`.well-known` Server Card」を優先項目に置いた以上（[MCP roadmap](https://blog.modelcontextprotocol.io/posts/mcp-roadmap/)）、ACL はいまからエージェント主体（tenant × agent × end-user の 3 軸）で設計し、`core`/`all` toolsets は progressive discovery に自然に乗る。組織境界を越える引き渡しには A2A v1.0 の署名付き Agent Card を出す（150+ 組織、Linux Foundation、[LF press](https://linuxfoundation.org/press/a2a-protocol-surpasses-150-organizations-lands-in-major-cloud-platforms-and-sees-enterprise-production-use-in-first-year)）。A2A は「メッセージ」を運ぶが引き渡し内容（決定・オープンループ・コミットメント・provenance）は無標準で、7 製品を試した検証は「メモリ可搬性は実質存在しない」と結論した（[dev.to](https://dev.to/stantyan/i-tested-7-ai-memory-products-for-portability-all-7-lock-you-in-31pm)）。ShogunAgent が A2A 引き渡し時に**型付き・provenance 付きの「state of work」オブジェクト**を出せば、ContextChain が指摘する「3〜4 回目の引き渡しで文脈が劣化する」穴を埋める。可搬性の標準は W3C AI Agent Memory Interoperability CG（2026 年 6 月憲章）と MIF/memorywire/OMP/OAMP が競合中で決着しておらず（[W3C CG](https://www.w3.org/community/ai-agent-memory-interop/)）、`state.export` と `shogun-memory-import/v1` を拡張した公開エクスポート形式（エンティティ、有効区間付き事実、provenance ポインタ、tombstone）を初日から出し、CG に参加するのが正しい賭けである。

アーキテクチャ面では、業界が「生の証拠 → 型付き・双時間・provenance 付き状態 → 要約」の三層＋背景統合に収斂した（Graphiti の `invalid_at`、supermemory の `updates/extends/derives`、Cloudflare の supersession chain、Mastra の Observer/Reflector）ことが、ShogunAI の event_log → state → period_summaries＋Dream Cycle をそのまま裏書きする。同時に **グラフ「エンジン」は退潮**している：Mem0 は traversable な `relations` を外してエンティティ・コレクションに替え、Graphiti は Kuzu を非推奨にし、Kuzu 本体は Apple 買収で 2025-10 にアーカイブされた（[Mem0 State of Memory 2026](https://mem0.ai/blog/state-of-ai-agent-memory-2026)、[The Register](https://www.theregister.com/2025/10/14/kuzudb_abandoned/)）。SQLite の型付き関係行（subject, predicate, object, valid_from, valid_to, provenance, confidence）と再帰 CTE で十分で、グラフ DB は買わない。埋め込みは fastembed-rs＋Qwen3-Embedding-0.6B または nomic をローカル既定にし（MemDelta は埋め込みモデルの差し替えだけで精度が +6.2pp 動き結論が反転することを示した、[arXiv 2606.29914](https://arxiv.org/abs/2606.29914)）、ベンチマーク全腕で固定する。ベンチマークそのものは LoCoMo を追わない：Penfield Labs の監査で解答キーの 6.4% が誤りで理論上限 93.6%、既定の LLM 採点者は意図的な誤答の 62.81% を受け入れた（[Penfield Labs](https://dev.to/penfieldlabs/we-audited-locomo-64-of-the-answer-key-is-wrong-and-the-judge-accepts-up-to-63-of-intentionally-33lg)）。信頼を得る方法は、OmniMemEval と Mem0 公開ハーネスでの**同一ハーネス走行**（reader/judge 明記、≥10 seed、信頼区間、1 回答あたりの文脈トークン、書き込み経路コスト、p95）と、誰も測っていない「異種イベントストリームからのオープンループ／コミットメント追跡」ベンチマークを自分で定義することである。memory-bench の既知の弱点——temporal で recall@1 0.000（古い値が常に 1 位）、abstention で false-evidence 100%（relevance floor が無い）——は、同一ハーネス公開の前に `since_ts/to_ts` と relevance floor で閉じる必要がある。

セキュリティとコンプライアンスは機能である。MINJA（[arXiv 2503.03704](https://arxiv.org/abs/2503.03704)）に代表されるメモリ汚染は OWASP Agentic Top 10 の ASI06 に入り、推奨緩和策——書き込み経路での検知、provenance、高リスク書き込みの人間レビュー——は `sanitize::persist_body`、`state_provenance.quote`、L2/L3 承認として実装済みである。Anthropic の memory tool が「中断を前提に進捗を常に書け」と注入する以上、エージェントは**タスク状態を絶えず書く**；ShogunAgent は agent-scratch 名前空間を principal のワールドモデルから分離し（研究が「authority-conditioned mutability」と呼ぶ未解決問題、[arXiv 2606.30306](https://arxiv.org/pdf/2606.30306)）、全書き込みに actor を記録しなければならない。MemClaw の本番バグ——サブテナントの GET-by-id でスコープ迂回、同期的な近似重複ゲートが非同期の矛盾検出より先に矛盾書き込みを拒否（[arXiv 2606.24535](https://arxiv.org/abs/2606.24535)）——は、そのままハーネスのテストケースにする。ユーザー保持鍵による暗号化は商用メモリベンダーに存在せず（AWS は CMK のみ）、SQLCipher＋Keychain 鍵の既存設計は「鍵をユーザーが持つ」階層として売れる。

## 「OpenRouter for Agents」も建てる。ただしルーターは入口、状態層が堀

オーナー判断により、Monid 型の汎用ツール・アグリゲータも建てる。技術的には難しくない：Monid のコネクタ・エンジンは MIT で、`discover`／`inspect`／`run` の 3 動詞と宣言的なコネクタ定義（provider / endpoint / zod スキーマ / 記録済み fixture）は再現でき、計量・認証・ゼロ保持プロキシは `apps/api` に既にある。調査が示した五つの警告——コネクタ・コードはコモディティ（MIT、780 フォーク）、中央値 $0.0015/call の薄利（OpenRouter は約 5% テイクで年換算 $140〜160M、約 $2.5B の中継支出の上に成り立ち Stripe に $7B 超で買収、[Sacra](https://sacra.com/c/openrouter/)）、Arcade による Smithery 買収と Stripe による OpenRouter 買収という統合、自社製品を自分で順位付けする利益相反、記憶は per-call スポット市場に合わない——は消えないので、**それらを設計条件として取り込む**。

Monid（Monid Inc.、SF）は 2026-04 にローンチし $9.8M を調達、`api.monid.ai` の `discover`／`inspect`（無料）／`run`（従量）と一つのプリペイド・ウォレット（または x402 の USDC）を持つ（[Yahoo Finance](https://finance.yahoo.com/technology/ai/articles/monid-7-7m-seed-signals-065006248.html)、[GitHub](https://github.com/monid-ai/monid)）。ランキング上位は TinyFish（754K 呼び出し）、TikHub、Context.dev、AnyAPI、Litescrape とすべて Web 検索／スクレイプ／ソーシャルデータで、記憶・知識・状態のカテゴリは存在しない（[monid.ai/rankings](https://monid.ai/rankings)）。独立レビュー（2026-08-22）は、1 サプライヤー（TikHub）が端点の 56%、`discover` が 26 倍高い端点を 1 位に出し（`scoreBreakdown` に価格水準が無い）、`/terms` と `/privacy` が 404、per-key 予算が無いと報告した（[Notis review](https://www.notis.ai/blog/monid-review/)）。「0% markup」と「10% プラットフォーム手数料」という収益モデルの矛盾も未解消である。これらが、後発が埋めるべき穴の一覧になる。

### 設計条件

1. **二層構造。** Router（discover/inspect/run、従量、ゼロ保持プロキシ）と State（ShogunAgent）。ルーターの粗利はほぼゼロで良い。目的は配布と「どのツールがどのタスクに効いたか」のデータであり、収益は ingest と状態側で測る。ルーターの KPI は売上ではなく**ルーター経由のエージェントのうち状態層を使い始めた割合**。
2. **コールドスタートは借りる。** コネクタ定義を Monid の形式（`provider.ts`、`endpoint.ts`、zod、fixtures）と互換にして既存約 1,600 端点の定義を取り込める形にし、Monid の hosted カタログを Proxy/Direct-use でパススルーする（再販業者 Notis が +20% で使った経路）。自前コネクタは差別化領域だけに集中する：日本 SaaS（freee／kintone／Sansan／Chatwork／CloudSign／LegalOn。主要 100 のうち 65% に MCP が無く、法務・電子契約は MCP ゼロ、[Zenn](https://zenn.dev/kanseilink/articles/a316f473d8d506)）、記憶・状態、承認を要する書き込み系。`shogun-integrations` は `Service` enum → `endpoints.rs` → `toolmap.rs` → `result.rs` の 4 点で新サービスを足せる。
3. **全 run に L1/L2/L3。** Monid にはワークスペース単位の予算しか無い。読み取りは L1、ユーザーデータに触る書き込みは L2（MRTR `input_required`）、外部送信・決済は L3（URL elicitation）。`scope.rs` の「表に無い操作は拒否、ExternalSend は必ず L3」（`tests/invariant4.rs`）をそのまま載せる。これが「エージェントが安全に金を使えるルーター」という売り文句になる。
4. **ルーターがユーザー所有の状態で学ぶ。** tool × task × outcome を ShogunAgent の state に記録し、`discover` のランキングを per-user／per-tenant に個別化する。Monid はこのデータ（session-id、hints、dispute）をルーター側に中央集権化しているが、ここでは持ち出し可能なユーザーの状態として持つ。これが乗り換えコストになり、ルーター単体では成立しない堀を状態層が作る。
5. **利益相反の処理。** スコア内訳に価格を含めて公開し、自社ツールは first-party ラベルで分離表示、自己優遇しないポリシーを文書化する。OpenAI の提出規約「他プラグインへの誘導禁止」（[OpenAI guidelines](https://developers.openai.com/apps-sdk/app-submission-guidelines)）に抵触しないよう、ディレクトリ提出物とルーターの SKILL.md は分ける。

### 技術メモ

MCP 2026-07-28 の Streamable HTTP 単一エンドポイントで、`discover`／`inspect`／`run` を MCP ツールと REST の両面に出す。`Mcp-Method`／`Mcp-Name` ヘッダでボディを解析せずに計量し、`apps/api` の Ed25519 認証と reserve-then-settle 台帳をそのまま使う。プロバイダ鍵は transport 層で注入し、エンジン・プロセスには入れない（Monid と同じ）。本文はログ・DB・メトリクスに残さない。SKILL.md は Monid の骨格（トリガー条件と非トリガー例外、バージョン一致規則、setup/auth、優先順位、コスト警告、ステータス、番号付きルール、[monid.ai/SKILL.md](https://monid.ai/SKILL.md)）に L2/L3 の意味を足す。x402 の受け入れは後段で判断し、それまではカード入金のウォレットと 402 規約で動かす。

**載ることも続ける。** 自前ルーターを持つことと他所に載ることは両立する。優先順に、公式 MCP Registry（`server.json`、公開 Streamable HTTP 端点）、Anthropic directory（`claude plugin validate --strict`、MCP サーバーはコネクタとして提出可）、Smithery（`smithery.yaml` か `/.well-known/mcp-config`）、Glama（GitHub から自動索引）、Composio toolkit、OpenAI Plugin directory（`readOnlyHint`/`destructiveHint`/`openWorldHint` 必須）。Monid には記憶カテゴリが `connectors/categories.ts` に追加された時点で `presets.usage.perCall()` の per-call provider として掲載する。L1/L2/L3 は MCP アノテーションに直接写像でき（Read → `readOnlyHint:true`、L1 → `destructiveHint:false`、L3 → `destructiveHint:true` かつ `openWorldHint:true`）、全ディレクトリの入場券になる。

## 決定事項：何を建て、何を建てず、どの順で進めるか

**ポジショニングの判定。** 「AI エージェントが装着する、仕事の状態（state of work）レイヤー」。一文で言えば *"Calibrated truth about your work — people, projects, commitments and open loops — inferred locally, with provenance on every fact and a human gate on every send, shared across all your agents over MCP."* 競合比較の軸は「記憶 vs 状態」「事実の自由文 vs 型付きテーブル＋confidence」「クラウドファースト vs ローカル既定」「削除ツールを渡さない vs L1/L2/L3 を型で強制」「Recall@20 vs 同一ハーネス公開」。`docs/gpt6-astra-implications.md` の結論「Computer Use を自作せず、Astra 級実行エンジンにワールドモデルと承認境界を貸す側に回る」と、`docs/positioning-category-messaging.md` の 5 層（L1 取得／L2 ハーネス＝ワールドモデル／L3 実行／L4 24 時間／L5 自己改善）のうち L2 を切り出して売る、という既存の方針と整合する。

**まず建てるもの。** 再利用するクレートと部位：`shogun-memory`（`state.rs`、`state_provenance`、`loops.rs`、`entity_pages.rs`、`recompute.rs`、`search/federated.rs`・`terms.rs`・`lexical.rs`、`sanitize.rs`、`traceability.rs`、`memory_import/`、`period_summaries.rs`；V1〜V91 を SQLite のまま使い、`tenant_id`／`uid`／`actor` を**加算マイグレーション**で足す）、`shogun-fusion`（`confidence.rs`、`assemble.rs`、`budget.rs`、`compress.rs`）、`shogun-agents`（`permission.rs`、`approval.rs`、`engine.rs`、`entitlement.rs`）、`shogun-redact`（全部）、`shogun-license`（verify 部）、`shogun-mcp`（`backend.rs` の `MemoryBackend`、`memory_api.rs` の `ApiLevel`/`tool_level`、`scope_allows`、`toolsets.rs`、`source_policy.rs`、`rate_limit.rs`、`rest_routing.rs`/`rest_auth.rs`、`mcp.rs`；Keychain 依存の `memory_api_settings.rs`/`live_tokens.rs`/`launcher_check.rs` は環境変数＋`apps/api` 発行トークンに差し替え）、`shogun-core` の中立部（`dreamcycle/{plan,hourly,session,prefilter,loops,pages,entities}.rs`、`llm/*`、`ai_search`、`context.rs`、`chat_grounding.rs`、`src/bin/shogun_api.rs`／`shogun_mcp.rs`）、`apps/api`（`auth.ts` の Ed25519／`meterSubject`、`usage.ts`/`spend.ts`/`pg-store.ts` の reserve-then-settle、`schemas.ts`、`/v1/review`、ゼロ保持ロガー）。新規に書くもの：(1) Streamable HTTP MCP（2026-07-28、`Mcp-Method`/`Mcp-Name`、`ttlMs`、MRTR）と `memory.ingest`/`memory.recall` の 2 ツールを足した **core 22 本**；(2) テナントごとの SQLCipher ファイルを開閉するサイドカー（Linux、`SHOGUN_DB_PATH` のテナント化）；(3) API key（`sa_` 接頭）＋OAuth/CIMD のエージェント認証；(4) `/memories/**` 仮想ファイルシステム射影（`memory_20250818` 互換）；(5) 公開エクスポート形式；(6) SKILL.md（Monid の骨格：トリガー条件と非トリガー例外、バージョン一致規則、setup/auth、優先順位、コスト警告、ステータス、番号付きルール、に L2/L3 の意味を追加）、Claude Code プラグイン、`server.json`；(7) 同一ハーネス・ベンチマーク公開（OmniMemEval＋Mem0 ハーネス）と「open-loop tracking」ベンチ v0；(8) **ルーター骨格**：`discover`/`inspect`/`run` を MCP ツールと REST の両面に、Monid 互換のコネクタ定義、Monid hosted カタログのパススルー、日本 SaaS 読み取りコネクタ 4 本（freee/kintone/Sansan/Chatwork）、記憶・状態カテゴリ、キー別ハード上限、全 run に L1/L2/L3、プリペイド・クレジットと 402。

## 結論

この調査が変えた理解は二つある。第一に、「エージェント向けメモリ」という言葉はもう市場カテゴリではなく、少なくとも四つの別製品（型付きビジネス知識、証明付き学習、セッション状態、ユーザー個人化）の総称であり、ラボが無料で出すのは最後の一つだけだという点である。ShogunAI が 2 年かけて作った「provenance と confidence を一箇所で強制し、送信を型で L3 に閉じ込める」仕組みは、個人化記憶の世界では過剰設計に見えたが、仕事の状態を複数のエージェントに貸す世界では最低要件になる——OWASP ASI06、EMNLP 2026 のライフサイクル調査、MemClaw、a16z の「生きた corpus」が、別々の方向からその同じ要件に収斂している。第二に、Monid と OpenRouter の分析が示すのは、エージェント経済で「集める」側（ルーター、レジストリ、ウォレット）は決済・認証の既存勢力に吸収されつつあり、独立して残るのは「状態を持ち、継続で価値が増え、乗り換えが痛い」層だという点である。だからルーターは建てるが入口として建て、堀は状態層に置く。

実行上の含意は、ShogunAgent を「新製品」ではなく「`shogun_api` バイナリの多重化と Memory API のブランド化」として始め、ルーター骨格を同じフェーズで並走させ、コードより配布（SKILL.md、プラグイン、レジストリ、同一ハーネス公開）に重心を置くことである。既存の Mac ユーザーは初日からワールドモデルの最良ソースを持つ顧客であり、彼らのエージェント（Claude Code、Codex、Cursor）はすでに `read` 接続を自動投入されている。残る問いは「日本の購買担当がこの準拠の形を評価するか」「Mac を持たない開発者が取り込み API だけで十分な状態を得られるか」「ルーター経由のエージェントが状態層に転換するか」の三つで、いずれも design partner の実測で答えが出る種類の問いである。
