## 0. 本書の位置づけ

「ハーネス」= SHOGUN がモデルを呼ぶ全ての機構。プロンプト構築、コンテキスト組み立て、モデル選択（ルーティング）、実行ループ（tool use）、予算・レート制御、計測、そしてそれらの品質を評価し改善し続ける仕組みまでを含む。

本書は3つの入力を統合したもの:

1. **コード実査**（`crates/shogun-core/src/llm/` 約4,200行＋呼び出し側全域の棚卸し）
2. **外部リサーチ: ルーティング/コスト/レイテンシ最適化**（FrugalGPT, RouteLLM, GPT-5ルーター事例, ベンダー価格・キャッシュ仕様, Anthropic のエージェント設計ガイド等）
3. **外部リサーチ: 評価と継続改善**（LLM-as-judge の較正手法, メモリ/パーソナルアシスタント向けベンチマーク, プライバシー制約下のオンライン評価, GEPA/DSPy, 評価駆動開発の実務手法）

結論を先に:

- **現状のハーネスは「配管」は一級品**。レーン分離の型レベル強制、テキストを持てない traceability、SLO ヒストグラム同梱、モック可能なトランスポート。この土台は変えない。
- **一方で「頭脳」と「目」が欠けている**。トークン計上ゼロ、コスト可視化ゼロ、プロンプトに同一性なし、プロンプトキャッシュ未使用、structured outputs 未使用、tool use は書かれているが未配線、そして**生成品質の評価が一切ない**（全 eval 資産は検索品質のみ）。
- 最適化の順序は「①計測できるようにする → ②タダで拾える性能を拾う（キャッシュ/構造化出力/Batch生成経路の配線）→ ③評価基盤を建てる → ④評価に基づいてルーティングと自律度を調整し続ける」。学習型ルーターや multi-agent fan-out のような派手な施策は現時点では**やらない**（§4.4）。

### 1.2 書かれているが未配線（死んでいるコード）

- **Tool use（#81 の中核）**: `shogun-mcp/src/tool_loop.rs`（`run_read_loop`, `MAX_TOOL_USES=8`）と `tool_catalog.rs` は実装・テスト済みだが、production の呼び出し元ゼロ。リクエストビルダは `tools` 配列を一切出さない。
- **Batch 生成経路**: `ModelClass::Brief` はワイヤ定義・relay 側マッピング（Sonnet 級）まで存在するが、送信するデバイスコードが無い。結果、Morning Brief の本文と圧縮サマリは**抽出型（先頭文結合）のまま**で、FR-MB-01（Batch 生成）を満たしていない。
- **コンテキスト圧縮**: フル実装済みだが `SHOGUN_COMPRESSION=1` 必須で既定 OFF。設定 UI なし。
- **鮮度減衰**: `trust.rs` の freshness decay は 1.0 固定。スコア重みも「計測後に校正」のまま未校正。

### 1.3 存在しないもの（本書の主対象）

> 4（プロンプトキャッシュ）は `llm::conversation::ChatRequest` ＋ `build_conversation_request` の
> `cache_control` 2 箇所（system / 直近履歴）で、6 のうちリトライは `stream_with` の「初デルタ前 1 回」で
> それぞれ実装済み。7 のモデル既定値は `llm::models::FAST_TEXT_MODEL` に集約（chat 既定は `inline_source.rs`
> のまま）。残りは本書の記述どおり。監査: `docs/audits/2026-09-10-frontend-backend-audit-and-fix-plan.md`。

1. **生成品質の評価が一切ない。** ゴールデンプロンプトセットなし、judge なし、出力品質の回帰ゲートなし。唯一の品質シグナル `grounding_pct()`（引用付き回答率）はメモリ内・当該起動のみ・非永続。
2. **トークン計上・コスト可視化がデバイス側にない。** レスポンスの usage をパースしていない。唯一の見積もりは `fusion::budget` の文字比ヒューリスティック（±10%）。relay はチャンク数しか数えない。`max_tokens` は呼び出し箇所ごとの固定定数。
3. **プロンプトに同一性がない。** バージョンもハッシュも無く、`String::push_str` の連鎖が9箇所以上に分散。メトリクス行を「どのプロンプトが出したか」に紐づけられない。

5. **structured outputs 未使用。** JSON 契約はプロンプト文言＋手書き寛容パーサで担保。
6. **リトライ/バックオフが trait 層になく**、`meeting_translate.rs` にだけアドホックに存在。デバイス側のグローバル予算・レート制御なし。
7. モデル既定値がハードコード文字列2箇所（`inline_source.rs:125` / `App.tsx:5336`）で無検証。

## 2. 外部環境の要点 — 何が効いて、何がハイプか

リサーチ全文の要約。設計判断に効く結論のみ記す（価格は 2026-06 時点の Anthropic 一次情報＋2026-08 時点の調査。**採用前に必ず公式で再確認**）。

### 2.1 効くもの（レバレッジ順）

1. **プロンプトキャッシュを前提にした設計**。Anthropic のキャッシュは明示ブレークポイント式: cache write は入力の 1.25×（5分TTL）/2×（1時間TTL）、**cache read は 0.1×（90%引き）**。プレフィックス一致方式なので「凍結された安定プレフィックス」を作れた者だけが恩恵を受ける。SHOGUN の「常時プリアセンブル」原則はこの設計と完全に同型 — context cache をそのまま「キャッシュ可能プレフィックス」として組めば、**コスト90%減とプリフィル遅延除去が同時に手に入る**。フォーカス切替時のプリウォーム（先行リクエストでキャッシュを温める）が SLO-03（初トークン1s）の最強の保険になる。
2. **Batch API はバックグラウンド全部に**。全モデル一律 50% 引き、キャッシュと**重ね掛け可能**（キャッシュ済み Batch 入力は定価の約5%）。Dream Cycle / インデックス / Morning Brief は締切耐性があるので設計上ぴったり。必要なのは提出スラック（例: 7時のブリーフは深夜1-2時までに投入）とフォールバック経路だけ。
3. **タスクタイプによる静的ルーティング**。実務上もっとも信頼できるルーティング信号は「そのリクエストが何のタスクか」であり、SHOGUN は呼び出し時点でそれを常に知っている（分類か、要約か、ドラフトか）。Haiku級/Sonnet級/Opus級の 70/20/10 分配で FrugalGPT 級の削減の大半が、学習型ルーターのリスクゼロで取れる。既存の `ModelClass` サーバー側マッピングはまさにこの形で、**拡張すべきであって置き換えるべきではない**。
4. **ストリーミング＋並列 tool call＋structured outputs**。地味だが確実: 体感レイテンシはストリーミングが最大レバー、並列 tool 実行はマルチツールターンで最大3倍超の壁時計短縮（tool_result は1メッセージに全部まとめて返すこと）、スキーマ強制デコードはフォーマット失敗率を 5-10% → 0.1% 未満に落とす（再試行がほぼ消える）。
5. **オンデバイス小型モデルによる前処理**はプライバシー強制メカニズムを兼ねる（クラウド egress の前に分類/抽出/クエリ拡張をローカルで済ませる）。ただし #237（モデル非同梱・非ダウンロード）との整合が要る — Apple Foundation Models framework（macOS 26+、OS 付属、~3Bモデル、guided generation）は「同梱もダウンロードもしない」ので条文とは両立するが、対応最低 OS（macOS 14）では使えないため**あくまで任意加速**。要オーナー判断（§7）。
6. **予算ガードはコアプロセスで強制**。反復上限＋無進捗検知＋トークン/金額上限をアプリ層でなく Rust コアで（webview ゲーティングに頼らない、の既存原則と同型）。特にサブスク委譲レーンは資源が「ユーザーの月次クォータ」なので、暴走ループはドル以上に高くつく（不変条件5の注意書きどおり）。
7. **検索は lexical-first で正しい**。個人メモリのクエリは固有名詞・ID・日付など完全一致系に偏り、その領域では BM25/FTS5 が dense を上回る証拠がある。長文脈詰め込みは 32K-64K で multi-hop 合成精度が急落するため、「小さな高信号ワーキングセットを組む」現行方針が正解。パラフレーズ検索の穴は**LLM クエリ拡張**（Haiku 級/オンデバイスでクエリを同義語・キーワード変形に展開してから FTS5）で塞ぐ — 埋め込み復活より先にこれ。

### 2.2 ハイプ（今はやらない）

- **学習型/商用 LLM ルーターをインタラクティブ経路に置くこと**。85-98% 削減の見出しはベンチ条件の数字。GPT-5 の内蔵ルーターは初日に「壊れて」ユーザーの信頼問題に発展した — **見えないルーティングは対話トラフィックでは信頼リスク、バッチトラフィックではタダの金**。この教訓に従う。
- **Multi-agent fan-out を既定にすること**。トークン約15倍。Anthropic 自身が「広探索・高価値タスク限定」とスコープしている。パーソナルアシスタントのアクションは大半が狭く状態依存 — 単一ループ＋並列 tool call が既定。
- **「長文脈が RAG を殺す」**。single-needle ベンチの錯覚。
- **ベクトル検索の必須視**。#237 の FTS5-only 判断は現時点のエビデンスで防衛可能（クエリ拡張を併用する限り）。
- **アプリ層での自前 speculative decoding**。プロバイダ提供機能（predicted outputs 等）を使う場面で使えば足りる。

### 2.3 価格の要点（2026-06 Anthropic 一次情報。採用時に再確認）

| モデル級 | 入力 $/MTok | 出力 $/MTok | 備考 |
|---|---|---|---|
| Haiku 級 | 1.00 | 5.00 | 分類・抽出・ライブ系の主力 |
| Sonnet 級 | 2.00-3.00 | 10.00-15.00 | 生成の主力（新世代ほど安い逆転あり） |
| Opus 級 | 5.00 | 25.00 | 精度クリティカルのみ |

掛け算則: **Batch 0.5× × cache read 0.1× ≒ 定価の5%**。OpenAI 側（GPT-5 系: nano $0.05 / mini $0.25 / 本体 $1.25 入力）はサードパーティ集計のみで裏取り未了 — BYOK 既定値の見直し時に公式確認。

## 3. あるべき姿（to-be）— ハーネス設計原則

以下を SHOGUN のハーネス規約とする。CLAUDE.md の不変条件と同格の運用ルール候補（採用時に CLAUDE.md へ昇格）。

### R1. ルーティングは設計時の静的タスクタイプ表。学習型ルーターを置かない

`ModelClass` を唯一のルーティング語彙として拡張する。デバイスは常に「意図」を送り、モデル実名の解決は relay（Batch）またはローカル設定（Agent）に置く現行構造を維持。

| タスク | レーン | モデル級 | 現状 | to-be |
|---|---|---|---|---|
| 分類・抽出（Dream Cycle） | Batch relay | Haiku | ✅ `Classify` | 維持 |
| 会議 Recap | Batch relay | Haiku | ✅ `Summarize` | 維持 |
| Morning Brief 生成 | Batch relay | Sonnet | ❌ 未配線 | **`Brief` を配線**（H1） |
| ライブ要約/翻訳・Quick Translate | Agent（BYOK/委譲。2026-10-03 #782 で Select-KK Messages から移行） | プロバイダの budget モデル（`budget_only`） | ✅ | 維持 |
| チャット/ドラフト/Scribe | Agent（BYOK/委譲） | ユーザー選択（既定 Sonnet 級） | ✅ | 維持。委譲はCLI任せ |
| クエリ拡張（検索前処理） | ローカル or Agent Haiku 級 | - | ❌ なし | 新設（H3） |
| eval judge | 開発側 CI | 生成と別ファミリー | ❌ なし | 新設（H2） |

カスケード（安→高への昇格）は高価値・高頻度・曖昧な経路**1〜2本だけ**に限定する。第一候補は「commitment 抽出の確信度が state 書き込みに足りるか」— 昇格判定は生の logprob でなく較正済み確信度を使い、結果は**サイレント再試行ではなく `confidence` 列に接続**する（低確信は Fusion の既存ゲートが「〜の可能性」に落とす。ハーネスと世界モデルで確信度の意味論を一本化する）。

### R2. インタラクティブ経路は「凍結プレフィックス＋キャッシュ」前提で組む

- プロンプトを `[固定システム部 | 準静的コンテキスト部（context cache 由来）| 可変クエリ部]` の3層に再編し、前2層の**バイト安定性を保証**する（タイムスタンプ・乱序 join・都度変わる文言を混入させない。順序はソート固定）。
- Anthropic BYOK 経路に `cache_control` ブレークポイントを導入。フォーカス切替時（context cache 更新時）に**プリウォームリクエスト**でプレフィックスを書き込み、ユーザーが押した瞬間のリクエストは cache read（0.1×・プリフィルほぼゼロ）になる。
- 委譲レーン（CLI）はキャッシュを制御できない — それで良い（ベンダー側最適化に任せる）。relay 経由 Batch は relay 側でキャッシュ設計する（システムプロンプト共通化）。

### R3. バックグラウンド処理は Batch 一択、締切スラック込みで設計する

新しいバックグラウンド機能を Messages API で書くことを禁止する（旧例外だったライブ要約/翻訳は 2026-10-03 #782 で Agent lane へ移り、Select KK の同期 Messages を使う経路は無くなった）。Morning Brief は「深夜提出＋朝のフォールバック（Batch 未着なら現行の抽出型で出す）」を仕様化 — 現行の劣化設計（FR-MB-04）がそのまま使える。

### R4. structured outputs で再試行を殺す

JSON 契約系（分類・抽出・minutes・brief）は strict スキーマ強制へ移行し、手書き寛容パーサは防御の第二層に格下げする。構造の妥当性 ≠ 意味の正しさなので、フィールドレベル検証（serde 型＋値域チェック）は残す。

### R5. ストリーミング必須・並列 tool・tool_result 一括返却

- Agent レーンの全経路でストリーミングを維持（現状 OK）。委譲レーンの非ストリーミングは #110 の SLO 計測課題として既知 — p50/p95 実測が要件。
- #81 配線時（H1）: 複数 `tool_use` ブロックは並行実行し、結果は**1つの user メッセージに全部**入れて返す（分割返却はモデルの並列化行動を退化させる）。`MAX_TOOL_USES=8`・タイムアウト・16KiB 上限は実装済みの値を維持。

### R6. usage 計上を trait 層で必須にする（計測なくして最適化なし）

- `AgentClient`/`BatchClient` の戻り値に `Usage { input_tokens, output_tokens, cache_read_tokens, cache_write_tokens }` を追加し、プロバイダレスポンスの usage をパースする（全プロバイダが返す）。
- 新テーブル `llm_usage`（マイグレーション必須・ロールバック付き）: `(ts, route, purpose, model_class_or_provider, prompt_id, prompt_version, input_tokens, output_tokens, cache_read, cache_write, latency_first_token_ms, latency_total_ms, outcome)`。**テキストは持たない**（traceability と同じ規律。CI ガード `check-log-hygiene.py` の対象に追加）。
- これで「機能別・プロンプト別のコスト/レイテンシ/失敗率」が初めて見える。relay 側もチャンク数からトークン数計上へ拡張（OPEN-B2 の日次上限設計の前提数字になる）。

### R7. プロンプトに同一性を与える

- 全プロンプトを `prompt_id`（例: `inline_draft`, `chat`, `minutes`, `consolidation`, `brief`, `scribe`, `reply_draft`, `live_summary`, `live_translate`, `voice_edit`）＋ `version`（人手インクリメント）＋ `content_hash`（ビルド時計算）で登録するレジストリを `shogun-core` に新設。テンプレートエンジンは不要 — 現行の関数構築のままで良いが、**出口を1箇所にし、id/version/hash を usage 行と eval 結果に必ず刻む**。
- これが評価基盤（§4）の前提: 「どのプロンプト版がどのスコアだったか」を語れない限り、回帰も A/B も改善も成立しない。

### R8. 予算ガードは Rust コアで強制する

- 実行単位（1アクション、1チャットターン、1 Dream Cycle）ごとのトークン上限と反復上限をコア側で強制。超過は「途中で殺す」でなく上限を意識した graceful stop（プロバイダの task budget 系機能が使える所は使う）。
- **委譲レーンには月次ローカルメーター**を置く（`llm_usage` から集計）。閾値超過で「今月の委譲枠を使い切りそうです」を UI に出し、BYOK フォールバック導線を出す。#110 の「レート制限をSHOGUNの障害に見せない」原則の事前版。
- リトライ/バックオフを trait 層の共通ポリシーに昇格（`meeting_translate.rs` の実装 — 429→クールダウン、指数バックオフ上限4回 — を一般化）。

### R9. 検索は lexical-first＋LLM クエリ拡張。長文脈詰め込み禁止

現行の FTS5＋小ワーキングセット方針を維持した上で、チャット/検索経路にクエリ拡張ステップ（Haiku 級 or 将来オンデバイス）を追加。埋め込み再導入の議論は、H2 の retrieval eval で「拡張込み lexical の recall@k が不足する」ことが**数字で**示されてから。

### R10. 変更はすべて計測とセットで入れる

SLO 変更に p50/p95 添付を義務づける既存ルールを、モデル/プロンプト変更に拡張: **プロンプト・モデル・コンテキスト組み立てを触る PR は、該当 eval スイートの before/after を PR 本文に貼る**（H2 完了後に CI ゲート化）。

## 4. 評価基盤（to-be）— 「精度を測れる」を建てる

現状は生成品質の計測手段がゼロ（§1.3-1）。プライバシー制約（生データはデバイス外に出ない＝実ユーザーデータでの中央評価は不可能）を**前提**にした4層構成にする。同種の制約下で合成コーパス評価がオンライン結果と強く相関した先行事例（Canva の検索評価）があり、この構成は妥協ではなく実証済みパターン。

### Layer 0 — トレース可視化と週次エラー分析（前提、~1週）

- 開発ビルド限定のローカルトレースビュー（プロンプト・応答・usage・prompt_id）。チームの Mac での **dogfooding が唯一の「実データ」トレース源**になるため、これを一級資産として扱う。
- 週次 30-60 分の**オープンコーディング**（失敗トレースの自由記述注釈→失敗タクソノミーへ集約）。タクソノミーは repo 管理し、各項目は「対応する evaluator」か「未カバーと明記」のどちらかを必ず持つ。

### Layer 1 — SynthDay: 合成ワークデー・ゴールデンベンチ（最重要資産、~2-3週）

- ジェネレータ（スクリプト＋frontier モデル、Select-KK Batch レーンで生成）: ペルソナ → 時系列イベントグラフ → マルチソース合成ワークデー（画面テキストイベント、会議トランスクリプト、メール、カレンダー、Slack）＋**正解 state tables＋QAペア**。LongMemEval/LoCoMo/PersonaMem の生成レシピをそのまま流用できる。
- 初期規模: ペルソナ10体、能力あたり 20-50 タスク（実失敗から起こすのが最優先 — 完璧なスイートを待たない）。git 管理・バージョン付き。バグ報告は「合成再現ケース化 → ゴールデン追加」を標準フローにする（報告には記述だけ入り、データは入らない前提で、構造を模した再現をエンジニアが起こす）。

### Layer 2 — ステージ別オフライン eval スイート（CI ゲート）

決定論スコアラー優先、judge は残余のみ。1 スイート ≒ 1 週間ずつ積む:

1. **state 抽出**（最優先。世界モデルの根幹）: フィールド別 precision/recall/F1 を hallucination（精度分母）と omission（再現率分母）に分けて計上＋ provenance リンク妥当性（純コードチェック）＋**確信度較正曲線**（モデルの confidence が正解率を予測しているか — Fusion の confidence ゲートの意味論を保証する eval）。
2. **検索**: SynthDay コーパスで FTS5 経路の recall@k / precision@k。#237（埋め込みなし）判断を数字で防衛し続けるゲート。既存 `retrieval_eval.rs` / `memory-bench` を SynthDay に接続。
3. **要約忠実性**（Recap / Morning Brief）: ソース照合の claim 検証（MiniCheck 系の軽量 fact-checker）＋二値基準ルーブリックの LLM judge。judge 規律: **生成と別モデルファミリー**、pairwise は両順序で実施（位置バイアス相殺）、チーム手ラベル ~100 件で較正し乖離 >20% で再較正。1-10 点スケール採点は使わない（二値基準の合議）。
4. **エージェント/アクション**: サンドボックスのモック MCP 環境で**結果状態を検査**（カレンダーに入ったか、ドラフトが正しいスレッドか）。信頼性の見出し数字は **pass^k（k=3）**（1回75%成功は3回連続では42% — ユーザー向けエージェントで効くのは後者）。**「動いてはいけない」否定ケースを必ず含める**。既存 `invariant4.rs`（L1 から egress 経路に到達不能）はこの層の決定論的政策テストとしてそのまま昇格。

CI 統合: プロンプト/モデル/検索設定を触る PR で該当スイートを実行し閾値回帰でブロック。週次の全量スケジュール実行でプロバイダ側ドリフトを検知。**新モデルは無条件に安全と見なさない**（新リリースが特定能力を最大50%退行させた計測例がある）— モデル更新は全量再ベースラインとセット。

### Layer 3 — オンライン品質シグナル（プライバシー制約下）

明示フィードバック（👍👎）は応答率 1-3% しかない。主軸は**暗黙シグナルの集計のみ送信**:

- 事前列挙イベント語彙（Apple の集計型テレメトリと同じ設計原則: 語彙を先に固定し、自由テキストは決して送らない）: 提案 shown/accepted/dismissed/edited/undone、ドラフト edit-ratio **バケット**（比率計算はオンデバイス、送るのはバケット値のみ）、再生成回数、Morning Brief 開封/滞在、grounding 率。全イベントに `prompt_id`+`version` を付与。
- 送信系は既存 analytics 系統（PostHog、opt-out、`analytics.json`）に**イベント名を足すだけ** — 新系統を作らない（2026-08-08 統合決定に従う）。キャプチャ内容を載せない規約はそのまま適用。
- **オンデバイス・シャドー評価**: 候補プロンプトを Dream Cycle 内で現行プロンプトと並走させ（Batch レーン＝Select-KK キー、コスト2倍は予算計上）、state-diff の一致/乖離**統計だけ**をテレメトリへ。生データが最初からデバイス外に存在しないので、シャドーテストとしては理想条件。プロンプト A/B はフラグ割当をクライアント側で行い、結果指標は上記集計値 — ただしユーザー数が小さいうちは**判断の主重心はオフライン eval に置き、オンラインは最終サニティチェック**。

### Layer 4 — 自律度を eval スコアでゲートする

- アクション種別が L1（自動実行）候補になる条件を「当該スイートで pass^k ≥ 閾値」と定義する（昇格）。オンラインで acceptance 劣化・undo 増加が出たら**自動降格レビュー**。不変条件4（外部送信は常に L3）はスコアと無関係の床としてそのまま — eval はこの床を CI の決定論テストで検査し続ける。
- これにより「L1 に何を入れて良いか」が主観でなく数字の議論になる。

## 5. 継続改善ループ（to-be）

生データを集めないフライホイール。回る順に:

1. **入力**: (a) チーム dogfood トレースの週次オープンコーディング、(b) バグ報告 → 合成再現 → ゴールデン追加、(c) オンライン集計シグナルによる「どこに合成 eval 投資をするか」のランキング。
2. **改善**: 最低スコアのステージに対して **GEPA/DSPy 系のプロンプト最適化**を回す（実行トレースを自然言語で反省し Pareto フロンティアを維持する方式。RL 比 35 分の 1 のロールアウトで上回る現行 SOTA）。前提条件は「metric＝eval スイートが存在すること」— だから評価基盤が先。
3. **検証**: CI 緑 → フラグ付きロールアウト → Layer 3 で監視。
4. **将来の分岐（v1 スコープ外）**: Batch レーンの高頻度分類/抽出は、合成データで訓練した**小型 fine-tuned モデル**が数百例以上のラベルでプロンプティングを安定的に上回る領域。コスト圧が立った時の選択肢として設計だけ残す（評価はゴールデンセットで同一）。オンデバイス fine-tuning は #237 と衝突し ROI も悪いため**無期限見送り**。
5. **再ベースライン則**: プロバイダの新モデル出荷ごと・四半期ごとに全量再実行。飽和した eval（100% 張り付き）は回帰層へ降格し、より難しいケースで置き換える。

## 8. まとめ — 差分の本質

SHOGUN のハーネスは「安全に呼ぶ」機構としては完成度が高いが、「**うまく呼べているかを知る**」機構が存在しない。品質・コスト・精度・スピードの最適化は全て計測の従属変数であり、順序はこう固定される:

**測れるようにする（H0）→ 確実に得な施策を入れる（H1）→ 精度を定義する（H2）→ 定義に基づいて配分と自律度を調整し続ける（H3/H4）**

派手なルーターや multi-agent より先に、usage 1行のパースとゴールデンセット 20 件から始めるのが、このプロダクトにとって最短の道である。
