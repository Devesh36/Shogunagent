# 402 Payment Required

The gateway answers `402` whenever a metered call cannot proceed for a money reason. There are
two reasons and one shape. Implementation: `apps/api/src/billing/402.ts`; tests:
`apps/api/test/metering.test.ts`. The plan's wording is `docs/implementation-plan.md` §7.3.

## When

| `error.code` | Meaning | `next_action` | `payment.accepts` | `retry_after` |
|---|---|---|---|---|
| `payment_required` | The wallet's spendable balance (`balance − reserved`) is below the quoted cost. | `top_up` | `[{ rail: "card", url, method: "POST" }]` | `0` |
| `cap_exceeded` | A hard cap (per key or per principal, daily or monthly) would be crossed. Money does not help. | `retry_after` | `[]` | seconds until the period resets (UTC midnight, or the first of next month) |

Every metered route returns this shape: the `/mcp` proxy (classified from `Mcp-Method` /
`Mcp-Name`), and any REST route mounted with the same metering middleware. Free calls (`read`,
`protocol`) never 402 — a wallet at zero still reads its own state.

A router `run` (`POST /v1/router/run`, `router.run`) is refused by the same wallet (E32): the router
asks this gateway to hold the run's price (`POST /v1/internal/router/reserve`) and passes the
`payment` object of the answer to the agent, so the amount (provider price + one take), the rails
and `retry_after` are the wallet's own. The router keeps no balance of its own.

Nothing is reserved, forwarded or recorded on a 402. The call is a no-op; retrying it after the
remedy is safe.

## Body

```json
{
  "error": {
    "code": "payment_required",
    "message": "This call costs 6000 micro-USD and the wallet has 1000 spendable. Top up at least 5000 micro-USD, then retry the same request.",
    "next_action": "top_up"
  },
  "payment": {
    "amount_micro_usd": 6000,
    "unit": "ingest",
    "accepts": [{ "rail": "card", "url": "https://api.shogunaios.com/v1/wallet/topup", "method": "POST" }],
    "retry_after": 0,
    "balance_micro_usd": 1000
  },
  "usage": { "unit": "ingest", "quantity": 0, "cost_micro_usd": 0 },
  "latency_ms": 3
}
```

For `cap_exceeded`, `payment.balance_micro_usd` is replaced by `payment.cap`:

```json
{
  "error": { "code": "cap_exceeded", "message": "…", "next_action": "retry_after" },
  "payment": {
    "amount_micro_usd": 500,
    "unit": "ingest",
    "accepts": [],
    "retry_after": 43200,
    "cap": { "scope": "key", "period": "day", "limit_micro_usd": 1000000, "spent_micro_usd": 999600 }
  },
  "usage": { "unit": "ingest", "quantity": 0, "cost_micro_usd": 0 },
  "latency_ms": 2
}
```

Field notes:

- Amounts are integer micro-USD (1 USD = 1,000,000). `amount_micro_usd` is the exact figure the
  call would have reserved — the same number `POST /v1/quote` and `Mcp-Dry-Run: true` return.
- `unit` is one of `ingest`, `model_op`, `run`, `storage` (`/.well-known/pricing.json`).
- `usage` and `latency_ms` are present so the envelope matches a `200`'s (§7.2); the quantity is
  `0` because nothing was billed.
- `accepts` is ordered by preference. It holds the `card` rail; where `X402_ENABLED=1` an `x402`
  entry follows it (see "The x402 rail" below). Off by default and off in production
  (docs/decisions/0002-x402.md).

## Headers

| Header | Value |
|---|---|
| `PAYMENT-REQUIRED` | base64url of the x402-style JSON below |
| `Retry-After` | present only for `cap_exceeded`, equal to `payment.retry_after` |
| `Cache-Control` | `no-store` |
| `Content-Type` | `application/json` |

The header payload (decoded):

```json
{
  "x402Version": 2,
  "error": "payment_required",
  "accepts": [{ "rail": "card", "url": "https://api.shogunaios.com/v1/wallet/topup", "method": "POST" }],
  "next_action": "top_up",
  "payment": { "amount_micro_usd": 6000, "unit": "ingest", "accepts": [ "…" ], "retry_after": 0, "balance_micro_usd": 1000 }
}
```

`x402Version`, a string `error` and `accepts[]` are the fields x402's `payment-required`
convention puts at the top level; `payment` and `next_action` carry the plan's fields so a client
that reads only headers has the full quote.

## The card rail

1. The agent calls `POST /v1/wallet/topup` with its key and `{"amount_micro_usd": 10000000}`
   ($10; min $5, max $500). The answer is `201` with `url` (a Stripe Checkout page) and
   `next_action: "approve_at_url"`.
2. A human opens the URL once and pays (URL elicitation). The agent does not need to poll
   Stripe: the gateway's webhook (`POST /v1/stripe/webhook`) credits the wallet when Stripe
   confirms, idempotently by event id.
3. The agent retries the call that answered `402`, unchanged.

## The x402 rail (behind `X402_ENABLED`, off by default)

Decision: not accepted in production today; the implementation ships behind a flag so it can be
turned on without a release when the criteria in docs/decisions/0002-x402.md are met.
Implementation: `apps/api/src/billing/x402.ts` and the `/mcp` path in `apps/api/src/metering.ts`;
tests: `apps/api/test/x402.test.ts`.

With the flag on, a `payment_required` 402 appends:

```json
{ "rail": "x402", "scheme": "exact", "network": "eip155:8453", "asset": "0x…USDC", "payTo": "0x…",
  "amount": "6000", "maxAmountRequired": "6000", "maxTimeoutSeconds": 60,
  "resource": "https://api.shogunaios.com/mcp", "description": "…", "mimeType": "application/json",
  "extra": { "name": "USDC", "version": "2", "amount_micro_usd": 6000 } }
```

USDC has 6 decimals, so the atomic amount equals `amount_micro_usd`. `cap_exceeded` never offers it:
a cap binds x402-funded calls too.

To pay, resend the same request with `X-PAYMENT: <base64 of an x402 PaymentPayload>` (the v2 name
`PAYMENT-SIGNATURE` is also read). The gateway:

1. refuses a payload it has seen before: `402` with `error.code: "payment_replayed"` (a payment pays
   for one call; sign a new one);
2. verifies it through the facilitator (`X402_FACILITATOR_URL`, `POST /verify`) against the
   requirement for this call; a rejection is `402` `payment_invalid` with a fresh `accepts`;
3. reserves against the hard caps with `funding: "x402"` — the wallet is not touched;
4. forwards the call; when the core's reply is a `2xx` whose `Mcp-Quantity` reports the whole
   quoted quantity (the settlement contract in `docs/api/billing.md`, "Hosted `/mcp`"), it settles
   the payment (`POST /settle`) and the receipt at the quoted price, and answers
   `X-PAYMENT-RESPONSE` (also `PAYMENT-RESPONSE`): base64 JSON
   `{ success, transaction, network, payer }`, plus `X-Usage-Funding: x402`;
5. on anything else it settles nothing: the payment is not captured and the receipt costs 0. That
   includes a JSON-RPC error, a refusal or an idempotent replay answered with HTTP 200 (the core
   reports `Mcp-Quantity: 0`) and a partial ingest (an `exact` payment cannot be captured in part).

A facilitator outage before verification answers `503` and leaves the payload reusable. If the
settlement itself fails after a successful call, the call is not charged and
`X-PAYMENT-RESPONSE.success` is `false`. `GET /v1/receipts` shows `funding` per receipt.

## Client guidance

- Branch on `error.code`, then on `next_action`. Do not parse `message`.
- On `payment_required`, compare `payment.amount_micro_usd` with `payment.balance_micro_usd` to
  size the top-up; the minimum top-up is `$5`.
- On `cap_exceeded`, sleep `retry_after` seconds or send less. A key may lower its own caps
  (`PATCH /v1/keys/{id}`); raising them above the defaults needs `admin`.
- A `402` is never logged with the request body on the gateway side, and never includes it.
