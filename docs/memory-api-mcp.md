# Memory API — stdio MCP recipes (Claude Code, Codex CLI / ChatGPT desktop, Cursor, Claude Desktop)

SHOGUN’s Memory API is exposed three ways (invariant 6): **MCP** (`shogun-mcp` stdio), **REST** (`shogun-api`), and **CLI** (`shogun`). This doc covers the **stdio MCP** face for AI clients.

## Prerequisites

1. **Enable Memory API** in the dashboard: **MCP** → Memory API → On (also available in notch settings).
   Fail closed: if `memory_api.json` is missing or `"enabled": false`, `shogun-mcp` / `shogun-api` exit nonzero with a clear stderr message.
2. **Add SHOGUN to the app**: Settings → Memory API → Add to an app → **Add to <app>** (issue #963). This makes the app's **connection** and writes its entry; there is no token to copy.  
   - Each connection has a **scope**, chosen when you add it. **Read only is the default** (see [Token scopes](#token-scopes)).  
   - The entry names the app (`--client <id>`). The server runs only while that app's connection exists, and under its scope.  
   - Once **any** app is connected or any token is issued, an entry that names no app and passes no matching `SHOGUN_API_TOKEN` is refused. Before that, process-trust is allowed when enabled (dev DX), with every tool available.
3. An active Pro entitlement or trial is required. The server checks the plan on each tool call; the enable toggle does not bypass it.

## Where is `memory.db`?

On macOS the desktop app stores memory under the app data directory, typically:

```text
~/Library/Application Support/com.syogun.shogunai/
  memory.db
  memory_api.json      # enable + profile (display_name, role, prefs)
  l3_approvals.json    # shared L3 queue (MCP actions.execute ↔ Settings → Approvals)
  visual_recall.json
```

(`memory_data_dir` may nest one level; open Settings → Memory API once to create `memory_api.json` next to the live DB.)

Standalone bins use `SHOGUN_DB_PATH` (default `./shogun.db`). Settings resolve as:

1. `SHOGUN_MEMORY_API_SETTINGS` if set — **debug builds only**; a release binary ignores it (audit 2026-08-13 P0-3), else  
2. `<parent of SHOGUN_DB_PATH>/memory_api.json`

So the client entries below carry only `--client <id>` and `SHOGUN_DB_PATH` (plus the optional `SHOGUN_MCP_TOOLSETS`): the settings file is found next to the database, and the connection is in the Keychain.

L3 approvals resolve as `SHOGUN_L3_APPROVALS` if set, else `<parent of SHOGUN_DB_PATH>/l3_approvals.json`.

## Build the MCP binary

Release builds of the app ship the server next to their own executable (`ShogunAI.app/Contents/MacOS/shogun-mcp`), and Settings fills that path into every entry (see **Add to an app** below). A local build of the app, a development run from a build tree, and a standalone setup do not include it: build it yourself and use that artifact's absolute path. Enabling access does not connect a client, and no client configuration is edited without your confirmation.

```bash
cargo build -p shogun-core --features db --bin shogun-mcp --release
# binary: target/release/shogun-mcp
```

## Client entries (generated)

Every entry below, and every file in [`docs/examples/`](examples/), is generated by `shogun_mcp::client_config` (issue #400). The test `client_config::tests` fails when a copy here drifts from the code, so change the code and paste its output, never the snippet alone. Merge the `shogun-memory` entry into an existing config rather than replacing the file.

Nothing in an entry is secret (issue #963): `--client <id>` names the app, and whether that app may connect is its connection in SHOGUN, made with **Add to <app>**. An entry pasted by hand works only after that app's connection exists: choose **Add to <app>** (it also writes the entry), or **Connect <app>** to make the connection without editing the app's file.

### The older token form

Entries written before issue #963 pass `SHOGUN_API_TOKEN` instead of `--client` (through `${SHOGUN_API_TOKEN}`, `${env:SHOGUN_API_TOKEN}`, Codex's `env_vars`, or a pasted value in Claude Desktop). They keep working while their token is issued. **Add to <app>** replaces such an entry with the new one, and the dialog masks the old token in the change it shows. Revoke the old token afterwards in the token list.

## Token scopes

Issue #400 (owner decision 2026-09-25). Every token has one of two scopes:

| Scope | What it allows |
|---|---|
| `read` (default for a new token) | Only read tools (the `R` rows of the tool table, 85 of 158). Every write and `actions.execute` is refused. |
| `full` | Every tool at its own level, L1 / L2 / L3 as before. Every token issued before scopes existed is `full` and keeps working unchanged. |

- **Where it lives.** The scope sits on the token's own Keychain record, next to its SHA-256 verifier (`memory-api-tokens`). The token itself is never stored in plain text. A record without a scope (issued before #400) reads as `full`. An unknown scope name fails the whole record set closed.
- **Where it is enforced.** One predicate, `memory_api::scope_allows`, applied before anything runs: REST (and so the CLI) in `rest::route`, right after the token and plan checks; MCP in `tools/call`. On MCP the session runs under the scope of the token it started with.
- **What a refusal looks like.** REST answers **403** `{"error":"scope_insufficient","scope":"read","message":"…"}`. MCP answers a JSON-RPC error with code **-32004** and a message starting `scope_insufficient:`. Nothing reaches the backend or the approval queue. A missing or wrong token is still 401, and a locked plan is still `plan_required`, before any scope answer.
- **`tools/list`.** A `read` session does not list write tools, the same way `SHOGUN_MCP_TOOLSETS` narrows the list. Unlike toolsets, the hidden tools are also refused when called.
- **Seeing scopes.** `api.tokens.list` (MCP), `GET /v1/api/tokens` (REST) and `shogun api tokens` (CLI) return each token's `id`, `name`, `created_at`, `scope` and `client` (below), plus `caller_scope`, the scope of the token making the call. They never return a token or a verifier.
- **What a token can see.** The same response carries `access`: every tool by toolset group, with its level (`read` / `l1` / `l2` / `l3` / `per_action`) and the scopes that may call it, generated by `memory_api::access_listing` from `scope_allows`. Settings → Memory API shows the same list as **What the app can see**, filtered to the scope chosen for the next token.
- **Raising a scope is only in the app.** No API face can issue a token or widen one: to give a client write access, issue a new token with **Read and change** in Settings → Memory API and replace the old one. This follows the `connections.composio` precedent (#670, loosening refused outright, no L3 card): an approval card cannot hand a freshly minted bearer back to the caller without putting the secret through the AI, and a caller asking for more power over itself is the case least suited to a one-tap approval. Revoking narrows access and is direct, in Settings.
- **Copying a token (issue #979).** A token for REST or a script is shown once, with **Copy token**. SHOGUN puts it on the pasteboard itself, not through the webview, so it can mark it: `org.nspasteboard.ConcealedType` and `org.nspasteboard.TransientType` (<http://nspasteboard.org>; clipboard managers that honour them hide the value or do not record it) and `NSPasteboardContentsCurrentHostOnly` (Universal Clipboard does not carry it to your other devices). After 60 seconds SHOGUN clears the pasteboard, but only if it still holds that copy: the pasteboard's change count is compared with the one the copy left, so anything copied since is left alone. Pressing ⌘C on the shown token takes the same path. If SHOGUN cannot write the pasteboard, Settings says so and lets a plain ⌘C through, without the markers or the clear, so the token shown once is not lost. The rules are `shogun_mcp::token_clipboard`; the AppKit call is the desktop's `memory_api_copy_token`, which accepts only token-shaped text and never logs it.
- **Linked to an app.** A token issued with **Issue a token for <app>** (Settings → Memory API → Add to an app, before #963 replaced it with the app's connection) records that app on its Keychain record (`client`: `claude-code`, `codex-cli`, `chatgpt-desktop`, `cursor` or `claude-desktop`). Metadata only, never secret, optional: a token issued by name, or before this existed, has no `client` (`null` in `api.tokens.list`) and is an unlinked token. Older builds ignore the field. A malformed value fails the record set closed, like an unknown scope.
- **Remove also revokes.** **Remove from <app>** shows, under the exact change, **Also revoke the token issued for <app>**, checked by default. On confirm the entry goes first, then every token linked to that app is revoked, together with the tokens of an app that reads the same file (Codex CLI and the ChatGPT desktop app share `~/.codex/config.toml`, so removing one removes both entries). Unlinked tokens are listed in the dialog for revoking by hand in the token list. Revoking is in-app only: no API face revokes a token (open question for the owner since #676; `connections.disconnect` is the only "remove access" tool on the API).
- **A revoked token stops at once, without a restart.** The running `shogun-mcp` (stdio) and `shogun-api` (REST, and so the CLI) re-check the token on every call against a live copy of the token list (`live_tokens::LiveTokens`). After each change to the Keychain item (issue, revoke, Remove with revoke), the app replaces `memory_api_tokens.rev` next to `memory_api.json`: a timestamp only, no token, verifier or id. Each call `stat`s that file and re-reads the Keychain only when it changed; the list is also re-read at least once a minute, so a failed marker write never keeps a revoked token alive longer than that. A re-read that fails refuses every call (process trust included) until it succeeds. REST answers **401** `unauthorized`; MCP answers JSON-RPC **-32001** with a message starting `unauthorized:`, on `tools/list` and `tools/call`. Other tokens are unaffected, and a newly issued token works in a running `shogun-api` at once too. On stdio the start-up rule is applied on every call: a session that started under process trust (no token issued yet) is refused once the first token exists and the session has none. The steady-state cost is one `stat` per call, about 0.7 µs (p95 under 1 µs, Linux).
- **Finer scopes later.** Scopes are stored by name, so per-group or a `propose` tier between read and write can be added as new names without changing the storage.

## Add to an app (Settings, and `mount` on every face)

Settings → Memory API → **Add to an app** shows, per client, the generated entry and where it goes, and the vendor's own add command where one takes the env block (`claude mcp add …` for Claude Code). Each has a Copy button. `api.tokens.list` returns the same text as `mount.clients` (with the placeholder paths above, so a response never carries this Mac's user name); Settings fills in this Mac's `memory.db`. All of it comes from `client_config::mount_setup` (issue #400).

- **No token at all (issue #963, owner decision 2026-10-06).** The entry passes `--client <id>` and nothing secret. Whether that app may connect, and with what scope, is its **connection**: a record `{client, scope, created_at}` in the same Keychain item as the token verifiers (`memory-api-tokens`, field `grants`), so making or widening one takes a Keychain write, not an edit to a plain file. `shogun-mcp` checks it at start-up and again on every `tools/list` / `tools/call`, like a token. Nothing goes through the clipboard, a shell profile or `launchctl setenv`, so nothing secret can reach Universal Clipboard, a clipboard history, a dotfiles repository or another process's `launchctl getenv`. Apps sharing a config file share one connection: Codex CLI and the ChatGPT desktop app use `codex-cli`.
- **What this does not stop.** A program running as you on this Mac can start `shogun-mcp --client <id>` itself and use a connection that exists, at its scope. The token never stopped that either: it sat in `launchctl` (readable by `launchctl getenv`), a shell profile, or Claude Desktop's config file. Issue #979 adds a check of the code signature of the app that starts the server, for desktop apps whose signature is stable; see the next item for what is done and what is not.
- **Who started the server (issue #979).** For a connection with an expected signer, `shogun-mcp` checks at start-up that the nearest program above it that Apple did not sign itself (a shell, `env` or `launchd` in between is looked through) is signed by that app's vendor team (a Developer ID requirement pinned to the Team ID, so an Electron app's helper process passes too). Anything else (another team's program, an unsigned one, a process macOS will not describe, or only Apple's programs up to `launchd`, as when it is run from Terminal) exits with a `shogun-mcp: refused: …` line that names the app and the way back: update the app and SHOGUN, then **Remove from <app>** and **Add to <app>** again. The check only takes access away, and runs only for a connection that has an expected signer. The expectations are compiled into the binary (`shogun_mcp::launcher_check::EXPECTED_SIGNERS`), not kept in a file a program could rewrite. **Status: the table is empty**, so no connection is checked yet and start-up behaves as before: an app is added only after its Team ID and its MCP launch chain are confirmed on a Mac (`docs/ondevice-qa-2026-09-26.md` §3-11). Connections started from a terminal can never be checked, because the program above `shogun-mcp` is `node` or a shell: Claude Code, Codex CLI (and so the ChatGPT desktop app, which shares its `codex-cli` connection), Gemini CLI and other npm-installed CLIs. `connections[].launcher` in `api.tokens.list` says which applies (`any_program` / `signed_app`), and Settings shows it next to each connected app ("usable by any program on this Mac"). Open: a vendor that changes its Team ID is refused until SHOGUN ships the new value; a process that exits and whose pid is reused between the lookup and the check is judged as the new process (closing that needs the parent's audit token).
- **Read only unless you choose.** **Add to <app>** connects with `read` unless you pick **Read and change**. Adding again with the other scope changes it in place.
- **One click, after you see the change.** The app ships `shogun-mcp` next to its own executable (`ShogunAI.app/Contents/MacOS/shogun-mcp`, a Tauri sidecar signed with the app's identity; `docs/release-signing-and-distribution.md` §4-a), and Settings fills that path into every entry. For every client, **Add to …** and **Remove from …** first show a confirmation with the exact change (`client_install::mount_preview`: the commands that will run, or SHOGUN's entry before and after, how many other servers stay untouched, and where the old file is kept) and, for Add, the scope the connection gets; nothing is written or run until you confirm, and the confirmation applies only if the file or the command list is still what you saw. On confirm the entry is written first and the connection made second, so a failed write never leaves a connection behind. **Remove from …** takes the entry out and then the connection, so a copy of the entry left anywhere else stops working too. **Connect <app>** makes the connection alone, for an entry you paste yourself; **Disconnect** in the connection list removes it without touching the app's file. A copy of the app that cannot add itself offers the copyable setup with a placeholder server path and says why: a local build or a development run from a build tree has no bundled server (`server_missing`), and a copy running from a disk image or a translocated location has one at a path that will not last, so it asks you to move the app to Applications first (`server_not_installed`). **Remove from …** still works there, so an out-of-date entry can be taken out from any copy. When Cursor, Codex CLI or the ChatGPT desktop app already has an older SHOGUN entry (an old launcher, a build-tree path), **Add to …** says it replaces it; Claude Code's add always runs `claude mcp remove` first, so its older entry is replaced too.
- **One-click setup, previewed on every face (`install`).** Each client in `mount.clients` carries `install`, from `client_install::install_preview`: `method` is `vendor_cli` (Claude Code: SHOGUN would run `claude mcp remove shogun-memory --scope user`, then the same `claude mcp add … --scope user` shown above, and never opens `~/.claude.json`), `config_file` (Cursor's `~/.cursor/mcp.json`; Codex CLI and the ChatGPT desktop app share `~/.codex/config.toml`; Claude Desktop's `claude_desktop_config.json`) or `copy_only` (no client since #963); `file` is the file it would edit, `adds` the text or commands it would add, and `apply` is always `in_app_only`. The plan behind it (`client_install::plan_add` / `plan_remove`) touches SHOGUN's `shogun-memory` entry only: it refuses a file that does not parse, splices SHOGUN's entry into the text so every other byte and comment stays where it was, reads the result back and refuses unless it equals the original with only that entry changed, and shows a diff of SHOGUN's entry alone (an old entry's token-shaped or unknown env values masked; other servers' entries, which can carry their own keys, never shown, only counted). Applying it re-reads the file and refuses if it changed since the preview, keeps `<file>.shogun-backup`, and replaces the file atomically with its permissions kept.
- **Applying is in-app only.** No MCP tool, REST route or CLI verb writes another app's configuration, and none reads one: the API faces get the preview above, built from placeholder paths without opening any file. Like issuing a token (#676) and the Composio consent (#670), this is refused on the API outright rather than queued as L3: the change lands in a file outside SHOGUN, and an agent asking to wire itself (or another agent) into SHOGUN is the case least suited to a one-tap approval.
- **Mount count.** Each time a client starts the stdio server and its connection or token passes the gate, the server sends one anonymous `memory_api_mounted` event whose only property is the session's `scope` (`read` / `full`): no client name, no token id, no path (`shogun_core::analytics::mount`, owner decision 2026-09-26). It reads the desktop's `analytics.json` and sends nothing when the user turned analytics off, when that file is missing, or when the binary was built without `net` or a PostHog key. It goes out once, on a background thread, through shogun-core's analytics transport.
- **Claude Desktop is one click too.** It documents no way to read a variable into its config, so while an entry needed a token, a working one had to hold it in plain text and SHOGUN would not write it (invariant 7). The entry now holds nothing secret, so **Add to Claude Desktop** writes it like Cursor's. Quit and reopen Claude Desktop afterwards.


### Automatic connections: no meetings or screen recall until you allow it (owner decision 2026-10-20, audit F4)

Since 2026-10-14 the app connects the AI apps it finds with `read` access and no click. Any program running as you can start the bundled `shogun-mcp --client <id>` and use that connection, and the Keychain trusts that binary, so nothing asks. A connection the app made **on its own** therefore does not reach the two most sensitive sources until you allow them in the app: **meeting notes** (transcripts, minutes, speakers, meeting search rows) and **Visual recall** (the stored screen frames and the OCR text kept in memory as `screen_text`). Everything else about automatic connection is unchanged.

- **The marker.** Each connection in the Keychain item carries `sensitive_sources`: `withheld` or `allowed` (`memory_api_settings::ClientGrant`). The automatic connection writes `withheld` (`GrantOrigin::Automatic`); **Add to …** / **Connect** write `allowed` for a new connection, as before (`GrantOrigin::User`). Changing an existing connection's access keeps its setting, except that widening it to **Read and change** (`full`) allows them too. The app never changes a connection that is already there.
- **Connections stored before the marker existed** read by a safety rule (`legacy_sensitive_sources`): a `read` connection created on or after 2026-10-14T00:00Z (when automatic connection shipped) reads as `withheld`, because nothing stored says whether it came from a click (`memory_api.json`'s `auto_connected` is a display list in a plain file, so it is not trusted for this). An earlier connection, and any `full` one (only ever the user's choice), keeps every source. A `read` connection you added by hand after 2026-10-14 therefore needs the switch below once. An older build that rewrites the item drops the field, and the same rule applies again.
- **Turning it on is in-app only.** Settings → Memory API → Connected apps shows "no meetings or screen recall" on a withheld connection and a per-connection **Include meetings and screen recall** switch. Turning it on asks first; turning it off is direct (`memory_api_set_connection_sources`). Widening to `full` also allows them.
- **The API can only take it away.** `api.tokens.list` shows `sensitive_sources` per connection. `api.connections.restrict` (`POST /v1/api/connections/restrict`, `shogun api restrict <client>`, L1) withholds them from one connection; asking for `allowed` is refused (400 / MCP `-32602`). There is no API way to allow them.
- **What a withheld session gets** (`shogun_mcp::source_policy`, one exhaustive table over every tool):
  - *Refused* with `source_not_allowed` (MCP JSON-RPC **-32006**, `data.reason`), hidden from `tools/list`, before any argument is read: every meeting tool (`meeting.list`, `meeting.recap.get`, `meeting.transcript.get`, `meeting.search`, `meeting.speakers.*`, `meeting.templates.*`, `meeting.recap.export`, `meeting.recap.track`, `meeting.recap.edit`, `meeting.delete`), every Visual recall frame tool (`visual_recall.search_frames`, `get_frame`, `frame_text_lines`, `rescan_frame`, `delete_frame`), `export.write_file` (writes a Recap), and the tools the desktop runs on the whole memory with a model, where nothing can filter the text (`skills.run`, `skills.run.status`, `schedules.add`, `forms.plan`, `actions.execute`). The last group is already refused to `read` by scope; it matters only for a `full` connection the API narrowed.
  - *Filtered* in the data layer before anything is returned: `memory.search` (meeting and session-summary rows, and events whose source is `meeting` / `screen_text` / `screen_ocr` / `user_screenshot`, are dropped; other hits lose evidence pointers into them; the page is fetched at the cap first and cut back to the caller's limit), `memory.get_context` and `memory.read_session` (sessions fold AX `capture` rows only), `memory.get_events` (such ids come back under `withheld`, never their text), `memory.get_context_pack` (no such evidence) and `wiki.evidence` (no such excerpts). `memory.search` with `mode: "ai"` answers with the filtered keyword results, `reason: "sources_withheld"`.
  - Settings mirrors (`meeting.recap_prefs.get`, `visual_recall.status`, …), state rows and model-written summaries are unchanged.
- **Where it is enforced.** The MCP face reads the connection's setting from the same live Keychain list as its scope, on every call, and runs the call under it (`source_policy::with_access`); `DbBackend` and the `Db` reads behind it ask `source_policy::current()`. REST and CLI tokens are unaffected: they are user-issued and never a connection.
- **Not covered.** Derived memory is not traced back to its sources: state rows (people, projects, commitments, open loops), period summaries and the Evening Wrap lines can still say what a meeting or a screen led to, though never quote it through these tools. `launcher_check` (who started the server) is separate and its table is still empty.

## Core toolset, routing guide (issue #1066)

**Handshake.** Every `initialize` answers with `instructions`: a short routing guide (about 1.4 KB) saying which tool answers which question (right now, today / this week, find X, who is Y, what do I owe, meetings), that results and summaries are indexes and the source must be opened before quoting (`meeting.transcript.get`, `wiki.evidence`, the event ids in a context pack), and that sends are never automatic. A locked plan appends the existing explanation after it (issue #744); the plan is still never disclosed to a session whose token or connection is not accepted.

**`tools/list` defaults to `core`.** The stdio server lists a 20-tool core set (about 3k tokens of descriptors instead of about 12k) unless told otherwise. Choose with, in order:

1. `--toolset core|full|<group ids>` on the entry's command line (`shogun-mcp --client cursor --toolset full`).
2. `SHOGUN_MCP_TOOLSETS` in the entry's `env` block (`all` and `full` mean the same; a list such as `core,meeting,mail` adds groups).
3. Neither: `core`. The generated **Add to ...** entries carry neither, so they list core.

- `core` (always included): `memory.search` (with `limit`, `from_ms`/`to_ms`, `source_kind`), `memory.get_context`, `memory.get_periods` (stored hour/day/week/month summaries for a window), `memory.get_context_pack`, `memory.get_wrap`, `memory.append_note`, `profile.whoami`, `state.commitments.list`, `state.open_loops.list`, `state.people.list` / `.get`, `state.projects.list` / `.get`, `meeting.list` / `.search` / `.recap.get` / `.transcript.get`, `wiki.evidence`, `actions.execute`, `actions.status`.
- Other groups: `files` (`memory.fs`: `/memories` as files, the memory tool's operations), `governance` (`approvals.list`, `approvals.get`, `audit.list`, `acl.list`: remote approvals, the audit log and access grants, reads only), `import`, `state`, `meeting`, `mail`, `visual_recall`, `voice`, `skills`, `wiki`, `web`, `export`, `translate`, `settings`, `forms`. The full table is in [`docs/specs/mcp-tool-surface.md`](specs/mcp-tool-surface.md) §7.
- An unknown group id in the env var is ignored with one warning on stderr; in `--toolset` it is an error (the server refuses to start rather than list a different surface).

**Listing is guidance, not a boundary.** A tool outside the listed set still works when called by name, at its own approval level, if the connection's scope (`read` / `full`) allows it. Scopes, grants and the L1/L2/L3 levels are the enforcement; REST and CLI never read toolsets.

**Search size.** `memory.search` takes `limit` (default 20, max 50; REST `?limit=`, CLI `--limit`). `memory.get_periods` takes `page_size` (default 24, max 48) and caps each summary at 1,500 characters.

**Day / period summaries.** `memory.get_periods` (REST `GET /v1/memory/periods?from_ms=&to_ms=&page_size=`, CLI `shogun periods [--from-ms N] [--to-ms N] [--page-size N]`, `--limit` accepted) returns the stored `period_summaries` rows (written by the Dream Cycle) overlapping the window: hours for a span up to 36 h, days up to 10 days, weeks up to 45 days, months beyond; when the coarse level is not generated yet (today has only closed hours) it falls back to the finer level. The window defaults to the last 24 hours. Rows carry `model_written` and `stale`.

### `dream.status` actions (issue #285)

`actions` answers "what can I do about last night?" before anything is pressed, so a button never silently does nothing. Each entry is `{id, completes, enabled, disabled_reason, api}`: `id` is `run_now` or `retry_full`, `completes` is `now` or `later`, and `disabled_reason` is a code (never copy — each face maps it to its own strings) or `null` when `enabled`. `api` is always `false` on the API faces (issue #779): the run needs the app's verified backup and single-run guard, so it is pressed in the SHOGUN app, and an agent should tell the user that rather than look for a tool. The decision is the pure function `dreamcycle::actions::available` in `shogun-core`, so the desktop can render the same data later (invariant 6).

- **`run_now`** — the degraded, state-only cycle (FR-DC-01 縮退版) on local rules. Returns immediately; sends nothing to the relay, so the relay's daily cap, the Batch credential, the window and the battery do not limit it. Off only while a cycle is running (`already_running`) or when the plan does not cover the nightly review (`plan_inactive`).
- **`retry_full`** — the night's full cycle again (a resume when one is unfinished); results arrive later. **Not offered yet**: every face reports `not_offered` until the owner decides the two-button design ships (`RETRY_FULL_OFFERED` in `dreamcycle/actions.rs`). The rest of its rules are already decided and tested, and the column below shows them as they will apply once it is offered.

Reason → actions on a typical morning (the window closed within the catch-up allowance, nothing waiting at the provider). "unknown" means the serving process could not see the fact; an unknown fact never disables an action by itself, but the night's recorded reason still can.

| `night.reason` | `run_now` | `retry_full` (once offered) |
|---|---|---|
| `asleep` | enabled | enabled |
| `not_idle` | enabled | enabled (a press means the user is present; idle only guards unattended runs) |
| `low_battery` | enabled | enabled; `low_battery` if the battery is under the floor off power now |
| `interrupted` | enabled | enabled (resumes from the ledger, no duplicated work) |
| `submission_rejected` | enabled | `rejected_by_service` |
| `relay_unreachable` | enabled | enabled |
| `batch_expired` | enabled | enabled |
| `batch_pending` | enabled | `results_pending` (collected later, never resubmitted) |
| `daily_cap` | enabled | `daily_cap_reached` unless the relay reports room again |
| `plan_inactive` | `plan_inactive` unless the plan is now known active | same |
| `storage_error` | enabled | enabled (the press reports its own failure if the fault persists) |
| `no_new_data` | enabled | `nothing_to_review` |
| `unknown` | enabled | enabled |

Checked for `retry_full` in this order, first match wins: `not_offered` → `already_running` → `plan_inactive` → the reason's code above → the night's state (`already_done` when it completed, `window_open` while the window is open and the cycle has not run, `nothing_to_review` before any night could run) → `results_pending` when a submitted job waits at the provider → `outside_catch_up` when the window closed more than 6 hours ago and nothing is unfinished (the full cycle carries into the next night) → `batch_lane_unavailable` (no entitled licence token) → `daily_cap_reached` (the relay reports 0 left) → `low_battery`.

What each face can see: MCP and REST (`shogun-mcp` / `shogun-api`, and the CLI through REST) re-read the plan and whether an entitled licence token is on the device on every answer. The battery and the relay's remaining cap are not visible there and stay unknown.

Open owner decisions from #285, not decided here: whether the two-button design (`retry_full`) ships in the next slice; the 6-hour catch-up window (`WAKE_CATCH_UP_MS`, shared with sleep/wake); Friday → Monday (today the old result is shown with its date and marked stale, and `retry_full` would be `outside_catch_up` for Friday's night); and the owner's comment listing "daily cap → run button disabled", which assumed the run would use the relay — the shipped `run_now` is local-only, so it stays enabled at the cap.

Each carries a stable `key` (`person-N`, `project-N`, or `knowledge-N`) accepted by evidence/neighbors. The saved About You profile remains `profile.whoami`; extraction never overwrites it. Evidence is capped at 50 excerpts; neighborhoods at 12 shared-source matches. Low-confidence entries are excluded unless explicitly requested (`include_low: true` / `?include_low` / `--include-low`). Included uncertain rows retain confidence and `possibly`; a shared source is **not** a semantic relationship. These are review surfaces, not instructions or confirmed knowledge.

Use `shogun meeting export 42 --transcript` to read a particular archived meeting rather than accidentally exporting the newest session.

### Manual connection check

1. Enable Memory API in Settings and **Add to <app>**. Pick **Read and change** if you want step 3's note to succeed; with the default **Read only** it is refused with `scope_insufficient`.  
2. Point the client's entry (above) at `shogun-mcp` with its env vars.  
3. In Cursor agent chat: call `profile.whoami`, then `memory.get_context`, then `memory.append_note` with a short note.  
4. Disable Memory API in Settings → restart MCP → process should refuse to start (stderr: `Memory API is disabled`, naming the settings file it checked).

## Troubleshooting

When a client reports that the server failed to start, or every call fails, read the client's MCP server log: that is `shogun-mcp`'s stderr. The start-up checks print lines that start with `shogun-mcp:` (`shogun-api:` for REST), name the file they checked with the home folder shown as `~`, and never print a token (issue #744).

To see the same lines without a client, run the command from the client's entry with the entry's env vars and stdin closed. A refusal exits with status 1; a healthy start prints at most the notes below and exits 0 at end of input.

```bash
SHOGUN_DB_PATH="$HOME/Library/Application Support/com.syogun.shogunai/memory.db" \
  /Applications/ShogunAI.app/Contents/MacOS/shogun-mcp </dev/null
```

| stderr says | Cause | What to do |
| --- | --- | --- |
| `Memory API is disabled … (no settings yet at …)` | The entry is right, but the Memory API has never been turned on, so its settings file was never written. | Turn on Settings → Memory API. |
| `no Memory API settings at …` with `SHOGUN_DB_PATH is not set` | The entry passes no `SHOGUN_DB_PATH`, so the server looked in the client's working directory. | Replace the entry from Settings → Memory API → **Add to an app**. |
| `… points into an old dev.shogun.spike folder` | The entry, or a launcher script it runs, comes from a development build. | Replace the entry from **Add to an app**; delete the old launcher once the client works. Do not copy or migrate the database. |
| `… is outside SHOGUN's data folder` | The entry points at a different `memory.db`. | Replace the entry from **Add to an app**. |
| `SHOGUN_DB_PATH starts with ~ or names a variable such as $HOME …` | A hand-edited entry wrote `~/…` or `$HOME/…`. No shell runs between the client and the server, so the path arrives unexpanded and is read literally, relative to the client's working directory. | Write the full path, or replace the entry from **Add to an app**. |
| `Memory API is disabled … (checked …)` | The switch is off. | Turn on Settings → Memory API. |
| `the Memory API settings at … are not valid` | `memory_api.json` is damaged. Settings will not overwrite a file it cannot read. | Move that file aside, then turn on the Memory API in Settings to write a new one. |
| `could not load Memory API tokens securely (Keychain status N)` | The Keychain read was refused, for example Deny on the prompt that asks whether `shogun-mcp` may use your keychain. A refused read never counts as "no tokens issued". | Choose **Always Allow** and restart the client. The server re-reads its tokens while it runs, so a one-time Allow asks again. |
| `SHOGUN_API_TOKEN must match an issued Memory API token.` | An entry in the older token form (or one naming no app), while an app is connected or a token issued: its token is missing, empty, an unexpanded `${…}` reference, the placeholder, or not an issued token (for example revoked). The next line says which. | Choose **Add to <app>** in Settings → Memory API: it replaces the entry with one that names the app and needs no token. |
| `no app is connected and no Memory API token has been issued on this Mac …` | Nothing is connected or issued yet, so the session is trusted as the local user with full access; a token the entry passes is not checked yet. | Add SHOGUN to an app (or issue a token) to require one. |
| `SHOGUN is not connected to <app>` | The entry names an app (`--client`) that SHOGUN has no connection for: it was never added from this Mac, or it was removed. | In Settings > Memory API, choose **Add to <app>**. |
| `the Memory API is locked on this Mac (reason)` | The plan (below). The server still starts and lists its tools. | Follow the sentence after the reason. |

A locked plan is also explained to the client: the MCP handshake carries `instructions` with the reason, every refused `tools/call` keeps code `-32003` and its `plan_required:` message and adds `data: {"reason", "fix"}`, and REST answers `403 {"error":"plan_required","reason","message"}` (the CLI prints that body). The reason is never shown to a caller whose token is not accepted.

| reason | Meaning |
| --- | --- |
| `trial_ended` | The 7-day trial has ended and no paid licence is on this Mac. |
| `trial_not_started` | No trial clock on this Mac yet (setup not finished, or `onboarding.json` missing or unreadable). |
| `standard_plan` | A verified Standard licence: the Memory API is part of Pro. |
| `plan_refresh_needed` | A paid licence that has not been re-verified within its offline grace window. Open SHOGUN while online. |
| `plan_unverified` | The saved licence (`billing.json`) could not be read or verified. Refresh it in Settings → Plan & billing. |
| `plan_not_found` | This process cannot locate the app's plan files at all (for example `HOME` is unset). |

A token revoked in Settings, or a connection removed with **Remove from …** or **Disconnect**, stops a running server at its next call: the standalone servers re-read the token list from the Keychain without the in-process cache (`keychain_store::get_generic_secret_uncached`), so the change the app made is what they check.

## Streamable HTTP (`POST /mcp`, MCP 2026-07-28)

The `shogun-api` server (`SHOGUN_API_PORT`, default 7464) also serves the MCP face over HTTP at
`/mcp` (E4-T1). The transport is **stateless**: no `initialize` handshake, no `Mcp-Session-Id`,
one JSON-RPC request per `POST`; `GET` and `DELETE` answer 405. `server/discover` returns the
capabilities, `tools/list` and `resources/list` carry `ttlMs` / `cacheScope` (`private`: the
answer depends on the bearer), and a read's result carries the same hints under `_meta`.

Every request names what it does in headers so a gateway can meter it without reading the body:

```
POST /mcp
Authorization: Bearer <token>
Content-Type: application/json
Mcp-Method: tools/call
Mcp-Name: memory.ingest

{"jsonrpc":"2.0","id":1,"method":"tools/call","params":{"name":"memory.ingest","arguments":{...}}}
```

`Mcp-Method` is required and must equal the body's `method`; for `tools/call`, `Mcp-Name` is
required and must equal `params.name`. A mismatch or a missing header is refused with 400 before
anything runs. Every reply carries `Mcp-Method`, `Mcp-Name` (when a tool was named),
`Mcp-Protocol-Version: 2026-07-28` and, for `memory.ingest`, `Mcp-Quantity` (the items received).
The bearer is a REST token; it is authenticated on every request against the live token list.

### L2 and L3 on the MCP face (MRTR and URL-mode elicitation, E4-T2)

- An **L2** tool answers `resultType: "input_required"` with one `inputRequests` form (a single
  `confirm` boolean, the tool and its arguments). Resend the same call with
  `params.inputResponses: [{ "id": "l2_confirm", "action": "accept", "content": { "confirm": true } }]`
  to run it; `decline` or `cancel` runs nothing.
- An **L3** request (an `actions.execute` send, or any write that waits in the approval queue)
  answers `resultType: "approval_required"` with an `approval` block (`approval_id`, `level`,
  `url`, the `actions.status` poll). With `SHOGUN_APPROVAL_BASE_URL` and
  `SHOGUN_APPROVAL_SIGNING_KEY` set, `url` is `<base>/approve/<token>` (E15: the gateway's
  approval page; the token is signed, short-lived and decides once) and a URL-mode
  `inputRequests` entry carries it for the human; without them the human approves in the app and
  the agent polls `actions.status`. The text block keeps the pending envelope (`pending`,
  `approval_id`, `level`, `origin`) for older clients.

REST and the CLI keep their `202 pending` envelope with the same `approval_id`, and since E15 it
carries the same `url` and `next_action: "approve_at_url"` (three-face parity), plus the
`poll` path. A response that queued an approval also names its token in the
`X-Shogun-Approval-Token` header, so the gateway can notify Slack and webhooks without reading the
body.

### Remote approvals, audit log and access grants (E15 / E18)

The sidecar's approval decision API (`crates/shogun-mcp/src/remote_approvals.rs`,
`server_governance.rs`):

| Route | Who | What |
|---|---|---|
| `GET /v1/approvals` · MCP `approvals.list` · `shogun approvals list` | any agent key (read) | the principal's queued approvals as redacted summaries |
| `GET /v1/approvals/{id}` · MCP `approvals.get` · `shogun approvals get <id>` | any agent key (read) | one redacted summary: kind, tier, recipient class (never the recipient), a masked one-line preview, `created_at`, `expires_at`, status, decision |
| `GET /v1/approvals/{id}` + `X-Shogun-Approval-Token` | the gateway | the same summary, authorized by the signed token |
| `POST /v1/approvals/{id}/decide` `{decision, decided_by, nonce}` | the gateway (token) or the operator (`SHOGUN_ADMIN_TOKEN`; `shogun approvals decide <id> approve\|reject`) | approve or reject. Never an MCP tool; an agent's bearer is `403 human_only` |
| `GET /v1/audit?since_ms=&limit=` · MCP `audit.list` · `shogun audit` | any agent key (read) | the principal's audit log |
| `GET /v1/acl` · MCP `acl.list` · `shogun acl list` | any agent key (read) | scratch and Team grants |
| `POST /v1/acl/grant`, `/v1/acl/revoke` · `shogun acl grant\|revoke <json>` | the operator only | change a grant |
| `GET`/`POST /v1/teams` · `shogun acl teams\|team <json>` | the operator only (multi-principal) | define teams |

- **Decision token.** `sat1.<base64url(claims)>.<base64url(HMAC-SHA256)>` over
  `shogun-approval-v1.<base64url(claims)>`, keyed with `SHOGUN_APPROVAL_SIGNING_KEY` (shared with
  the gateway only). Claims: approval id, principal, expiry (the approval's own 10-minute window),
  nonce. A decision repeats the nonce; the sidecar spends it, so a replay is `409 token_replayed`,
  an expired token `410 token_expired`, a forged one `403 invalid_token`.
- **Durable ledger** (V103 `approval_decisions`, `approval_spent_nonces`, in the principal's own
  store). The spent nonce is written to the principal's store before anything is decided, and the
  decision (who, when, how, tier, execution state) right after, so a restarted sidecar still
  refuses a replayed token and still answers `approvals.get` / `actions.status` for a decided
  approval. A store that cannot record the nonce refuses the decision (`503
  approval_ledger_unavailable`, nothing decided). In multi-principal mode approval ids start above
  every id an earlier process handed out, so a persisted decision never names a later approval,
  and `actions.status` answers `unknown` for another principal's approval.
- **Approved, then executed.** A human's approval confirms with the dedicated button's authority
  and moves the request to `approved`. A sidecar built with the execution path (`shogun-api`,
  feature `exec`, multi-principal) then carries the action out **once**, in the same request: the
  principal's ledger claims it (`pending` → `executing`, a compare-and-set, so two racing
  decisions or a second process never run it twice), `send_exec` writes the traceability row to
  the principal's store and calls the provider with the principal's connector grant (from the
  token store; no grant is `not_connected`), and the outcome is recorded on the approval, in the
  ledger and in the audit log (`approvals.execute`, `sent` or `failed:<class>`). The decide
  answer and `actions.status` read `sent`, or `send_failed` with a `reason` class
  (`not_connected`, `not_authorized`, `connection_changed`, `trace_unavailable`,
  `invalid_target`, `not_executable`, `provider_error`, `timeout`, `ledger_unavailable`) — never
  the provider's message or the body. A rejected, expired or unknown approval releases no action
  and nothing runs. A build without the execution path (the `shogun-mcp` server alone, or the
  single-principal `shogun-api` beside the desktop app) leaves the approval `approved` with
  `next_action: "execute_unavailable"`. The decision is recorded with `decided_by` and the time in
  the ledger and in the audit log.
- **Audit log** (V101 `audit_log`): one record per write and per approval decision on every face —
  actor, principal, tool or route, tier, outcome (`ok`, `pending`, `refused`, `approved`, …),
  time, request id (`X-Request-Id`, echoed). Never a body or an argument value.
- **Scratch ACL** (V101 `scratch_acl`): an agent reads and writes its own `agent_scratch:<id>` and
  the world; another agent's scratch is invisible (search, lists, GET by id, `/memories` files)
  unless the operator granted `read` or `write`. Enforced in the data layer (`ReadScope`,
  `scratch_files`, `event_log` writes); a request body cannot name another agent as its writer.
- **Team** (multi-principal): `?principal=<other>` on a read reaches a teammate's store only when
  both are on one team (`teams.json` under the principal root) and the teammate granted
  `world_read` in its own file (V101 `principal_grants`). World rows only, never scratch or a
  write; results carry `"source_principal"`. Without the grant the answer is a 403 that is the same
  for every principal id.
